# MAX Фото

Сервис приёма фотографий из разрешённых чатов MAX: OCR → координаты → PostGIS → классификация работы → Яндекс.Диск. Операторы проверяют неоднозначные фотографии, исправляют дату и координаты, смотрят отчёты и скачивают Excel.

Результаты проверки кода, чистки и сохранности данных: [ревизия 18–19 октября 2026](docs/CODE_REVIEW_2026-10-19.md).

Новый сервис находится в `backend/` и `frontend/`. Старые `main.py`, `handlers/`, `downloaders/`, `services/`, локальные фотографии и существующий `.env` сохранены. Docker **не запускает старый загрузчик**. Не запускайте его одновременно с новым сервисом для того же бота.

## Что реализовано

Администратор задаёт названия папок компании в «Обмен с АРМ» → «Папки компании на Яндекс.Диске».
Основное имя используется для рабочих фото; учебные фото, спам и JSON получают суффиксы
`_TRAINING`, `_SPAM`, `_ARM_EXCHANGE`. Настройка хранится в БД и применяется всеми процессами.
До первого сохранения используются прежние значения `.env`; после него они остаются только
исходным архивом в истории настройки. Миграция `0026` добавляет пустую настройку без переноса файлов.

Новое имя предназначено для последующих загрузок. Существующие файлы и ссылки сохраняются;
исправление старого фото, перенос в спам и восстановление остаются в семье прежних папок.
Незавершённая передача сначала завершается по сохранённому плану. Уже подготовленная JSON-выгрузка
сохраняет свой корень; новые публикации используют новую папку обмена. Старые выгрузки при смене
названий автоматически не удаляются. Для АРМ нужно отдельно обновить путь чтения JSON.
Разделение ранее смешанного архива требует отдельного переноса и не выполняется сменой имени.

Перед сохранением проверяются все четыре папки. Существующий чужой или неопознанный архив
не используется; новая папка закрепляется за UUID этой установки служебным файлом
`_MAX_FOTO_OWNER.json`. После частичного сбоя создание можно повторить, файлы не перезаписываются.
Не удаляйте этот файл вручную. Оператор не может менять настройку даже с правом управления обменом.
Для установки обновите все компоненты сервиса одной версией с применением миграции `0026`.

В разделе «Новости» администратор и операторы с правом «Просмотр новостей» читают о новых
возможностях, смотрят инструкции и увеличивают скриншоты. По умолчанию право выключено;
статьи и изображения защищены на сервере. По поручению владельца к обновлениям проекта готовятся
публикации о новых возможностях с инструкциями и скриншотами.
Порядок подготовки и размещения публикаций: [NEWS.md](docs/NEWS.md).

Виды работ хранятся в базе и редактируются администратором в разделе «Виды работ». При обновлении существующего сервера переносятся **16 коротких маркировок из таблицы работ** с прежними внутренними кодами. На новой установке справочник пустой. Названия, объединение старых
категорий, новая структура папок и порядок обновления описаны в [WORK_CATALOG.md](docs/WORK_CATALOG.md).

При создании или изменении вида работ можно добавить необязательное описание до 2000 символов.
Оператор видит его по значку ⓘ рядом с видом работы: при наведении, фокусе с клавиатуры или
нажатии на телефоне. Подсказки доступны и при просмотре фотографии без права редактирования.
Миграция `0025` добавляет пустое поле описания к существующему справочнику; коды, привязки
фотографий, индексы обученной модели и пути файлов сохраняются. При обновлении нужно применить
миграции и обновить компоненты сервиса одной версией. Описания заполняет администратор.

- FastAPI, PostgreSQL 16 + PostGIS, SQLAlchemy, Alembic, React/TypeScript, Яндекс.Карты с редактором полигонов.
- Официальный MAX Bot API: webhook с секретом, разрешённые чаты в БД, повторная доставка без повторных записей, несколько вложений → один итоговый ответ.
- Изображения и файлы JPG/JPEG/PNG/GIF/TIF/TIFF/BMP/HEIC/WebP; проверяется реальное декодирование файла. Для GIF анализируется первый кадр.
- Пересылки отклоняются до скачивания. Дедупликация SHA-256 внутри тестового или рабочего режима до OCR/AI, уникальный индекс и блокировка при конкуренции. Тестовая копия не блокирует приём рабочего оригинала.
- Локальный PaddleOCR PP-OCRv5 mobile с русскоязычной моделью через RapidOCR/ONNX Runtime, Tesseract `rus+eng` как резерв. Независимые `OCRService`, `DateTimeParser`, `CoordinateParser`, `WorkTypeClassifier`.
- OCR сначала выделяет чёрную плашку, затем при необходимости проверяет низ и полный кадр. Части одной строки объединяются по расположению на изображении. Поддерживаются все сокращения русских месяцев, похожие латинские буквы (`anp.` → `апр.`), `apr.`, даты без пробелов (`10 нояб.2025`) и слитные координаты с обозначением полушарий (`61.1024N72.5793E`). Цифры не подменяются; противоречивые значения остаются на ручной проверке. Обучение классификатора работ не обучает OCR. Сравнение моделей и ограничения — в [OCR.md](docs/OCR.md).
- Локальная нейросеть PyTorch ResNet18 по редактируемому справочнику видов работ; существующая модель на 16 категорий сохраняется. Обучение по подтверждениям оператора, проверочная выборка, версии моделей и автоматическое дообучение в отдельном процессе. Фотографии не передаются внешнему AI API.
- Геопоиск только по координатам; Polygon/MultiPolygon, точка на границе, пересечения и выход за территорию; пересчёт после изменения границ.
- Оригиналы на Яндекс.Диске без перекодирования, контроль SHA-256 после загрузки, перенос/переименование после проверки. Локальный буфер сохраняется до подтверждения загрузки и фиксации БД. Назначение каждой передачи заранее сохраняется в журнале: после сбоя сначала завершается прежняя операция, затем применяются новые исправления карточки.
- Долговечная очередь в PostgreSQL, повторные попытки с задержкой, восстановление после остановки worker, административный список задач.
- Закрытая авторизация: Argon2id, сессии в HttpOnly-cookie, CSRF, ограничение попыток входа, ADMIN_OPERATOR/OPERATOR, отзыв сессий при блокировке и смене пароля.
- Отчёты по чатам, микрорайонам, работам, матрица чат × микрорайон; общие фильтры со списком фотографий и Excel из пяти листов.
- Аудит изменений, история фотографии, контроль версии при одновременном редактировании, выбор следующего фото в очереди.

## Запуск локально

Нужны Docker Desktop/Engine и Docker Compose v2. На Apple Silicon PostGIS запускается через amd64-эмуляцию; это указано в Compose. На обычном amd64-сервере эмуляция не используется.

1. Подготовьте `.env` по `.env.example`. **В этом репозитории `.env` уже существует: дополните его, не перезаписывайте сохранённый MAX-токен.** Для локального HTTP оставьте `APP_ENV=development`, `COOKIE_SECURE=false`, `APP_ORIGIN=http://localhost:8080`.
2. Укажите случайный `POSTGRES_PASSWORD` (удобно использовать hex-символы, поскольку он входит в URL БД), `MAX_WEBHOOK_SECRET` длиной от 32 символов, токены MAX и Яндекс.Диска. Для карты нужен `YANDEX_MAPS_API_KEY` — ключ JavaScript API из [кабинета Яндекса](https://developer.tech.yandex.ru/keys/). Ограничьте ключ доменом панели. Ключ отображения карты доступен браузеру; токены MAX/Диска туда не передаются.
3. Запустите:

```bash
docker compose up -d --build
docker compose exec api python -m app.cli create-admin --login admin --name 'Администратор'
```

Пароль вводится интерактивно и не попадает в командную строку. Публичной регистрации и встроенного пароля нет. Миграции выполняет отдельный контейнер `migrate`; API, worker, publisher и trainer стартуют только после успешной миграции.

4. Откройте [панель](http://localhost:8080), войдите, добавьте разрешённые чаты и нарисуйте реальные границы микрорайонов. Во вкладке «Чаты MAX» → «Обнаруженные чаты» ID появляется после нового сообщения в группе, где бот назначен администратором. Кнопка «Добавить чат» подставляет ID в форму; укажите название и настройки приёма, затем сохраните. Ручной ввод ID тоже доступен. В production нет фиктивных пользователей, чатов, полигонов и фотографий.
5. Настройте HTTPS и webhook по инструкции ниже. Локальный `localhost` недоступен MAX: для реального приёма событий нужен публичный адрес.

До обучения первой модели фотографии загружаются на Диск, а вид работы требует проверки оператором. На странице «Обучение нейросети» показано, сколько примеров ещё нужно. Без доступа к Яндекс.Диску оригиналы остаются в буфере, запись получает ERROR, задача повторяется. Качество OCR/AI нужно проверить на реальных фотографиях вашей камеры; синтетические тесты не подтверждают качество классификации всех 16 категорий.

## Собственная нейросеть и обучение

Распознавание работы выполняется на сервере с помощью ResNet18 и собственной выходной головы по видам работ компании. Существующие модели с 16 выходами продолжают работать без изменения весов; у новых моделей состав и порядок выходов сохраняются отдельно для каждой версии. OCR даты/координат также локальный — PaddleOCR, с резервным Tesseract. Внешний ChatGPT/Vision API полностью удалён из нового сервиса; старые `VISION_*` параметры больше не используются.

Готовые OCR-веса (около 12 МБ) скачиваются и проверяются по SHA256 при сборке Docker-образа. При обработке фотографий скачиваний моделей нет. Модель загружается в память один раз на процесс; `OCR_THREADS=2` ограничивает вычислительные потоки ONNX. Новые параметры можно не добавлять в существующий `.env`: PaddleOCR включён по умолчанию. Для возврата к прежнему OCR установите `OCR_BACKEND=tesseract` и пересоздайте контейнеры. Уже обработанные записи и ручные исправления автоматически не перезаписываются.

При первом обучении `trainer` один раз скачивает общие веса ImageNet с официального сервера PyTorch (около 45 МБ, проверяется хэш). Это начальные признаки изображений, а не готовая модель ваших работ. Дальше обучаются последний блок и классификатор на ваших снимках. Для сервера без интернета заранее положите `resnet18-f37072fd.pth` в `/data/models/` и установите `ML_DOWNLOAD_BACKBONE=false`. CPU-версия PyTorch входит в Linux-образ, GPU не обязателен. Начните с 4 CPU / 8 ГБ RAM; фактическое время и память зависят от объёма выборки и `ML_BATCH_SIZE`.

1. Оператор открывает фото, выбирает/подтверждает вид работы и сохраняет. В выборку попадают только явные подтверждения вида работы; автоматические прогнозы и исправления одной даты не считаются разметкой.
2. По умолчанию первый запуск требует 100 размеченных фото в подготовленных категориях, минимум 20 фото на категорию, минимум 2 категории. Для каждой категории нужны хотя бы 3 снимка в проверочной части и 2 в обучающей. Не все 16 категории включаются сразу — неготовые остаются на ручной проверке.
3. Около 20% снимков постоянно закрепляются за проверочной частью по SHA-256. Они никогда не участвуют в обучении, даже после изменения меток. Модель каждый раз учится на всей накопленной обучающей части, чтобы новые работы не вытесняли старые.
4. После 20 новых/исправленных/удалённых меток запускается следующий цикл. Период проверки — 60 секунд. Администратор также может нажать «Обучить сейчас». Процесс `trainer` отделён от очереди приёма фото.
5. Версия включается только при macro F1 ≥ 0,70. Автоклассификация категории требует precision ≥ 0,90 и recall ≥ 0,50 на проверочной части. Качество сравнивается с текущей моделью на той же выборке; ухудшение macro F1 или потеря поддерживаемых категорий блокируют замену.
6. При распознавании проверяются полный кадр и четыре перекрывающихся фрагмента. Низкая уверенность, неподтверждённая категория или противоречащие уверенные прогнозы отправляют фото оператору. Это эвристика неоднозначности, а не отдельный детектор всех объектов сцены.

Эти пороги задаются в `.env.example`; стартовые значения не являются обещанием точности. Для похожих работ (например, уборка/подметание) нужны разнообразные реальные примеры каждого класса. Страница обучения показывает состав выборки, метрики, ошибки и историю версий. Артефакты находятся в `/data/models/version-ID/weights.pt`, метки/метрики — в PostgreSQL. Превью в `/data/previews` служат локальными обучающими изображениями после отправки оригиналов на Диск.

Автоматически сохраняются **текущая модель и 3 предыдущие успешно проверенные версии той же архитектуры**. Более старые веса и файлы неудачных/прерванных обучений очищает `trainer` после завершения обучения и при периодической проверке (по умолчанию раз в минуту, в том числе при выключенном автоматическом обучении). Если активной модели ещё нет, остаются 4 последние завершённые версии с файлами. Если файл активной модели недоступен, очистка пропускается, чтобы сохранить резервные версии. Запущенное обучение и загрузка весов для распознавания защищены блокировками от одновременной очистки.

Очистка касается только `weights.pt` и `weights.tmp` в известных сервису папках `version-ID`; папка удаляется только если пуста. Фотографии, превью, разметка, исправления операторов, общие начальные веса ImageNet и записи истории обучения сохраняются. В истории видно, какие файлы уже удалены, а удаление фиксируется в журнале действий. При ошибке файловой системы или базы следующая проверка повторяет очистку. Для установки требуется миграция `0014` и обновление API, worker, trainer и интерфейса одной версией. Сама миграция файлы не удаляет; накопленные старые веса очистятся после запуска обновлённого `trainer`.

## Сервер и MAX webhook

По официальной документации, проверенной 30.09.2026, production-интеграции MAX используют webhook по HTTPS на порту 443. Long polling ограничен по скорости и сроку хранения событий, поэтому в новом сервисе он не используется.

1. Создайте/подключите бота через платформу MAX для бизнеса и получите токен. Добавьте бота в рабочие чаты с доступом к сообщениям.
2. Привяжите домен к серверу. Установите HTTPS reverse proxy; пример для Caddy — `deploy/Caddyfile`. Compose публикует только web на loopback, БД и API наружу не публикуются.
3. В `.env` установите:

```dotenv
APP_ENV=production
APP_ORIGIN=https://photos.example.org
COOKIE_SECURE=true
```

4. Для MAX проверка сертификатов **выключена по умолчанию**: `MAX_VERIFY_TLS=false` действует и на Bot API, и на скачивание его вложений. Для Яндекс.Диска и загрузки базовых весов TLS проверяется. При необходимости вернуть проверку MAX установите `MAX_VERIFY_TLS=true`; `MAX_CA_BUNDLE` используется только в этом режиме. Входящий HTTPS webhook и его секрет работают независимо от этой настройки.
5. Проверьте соединение и зарегистрируйте webhook:

```bash
docker compose exec api python -m app.cli check-max
docker compose exec api python -m app.cli subscribe --url https://photos.example.org/api/webhooks/max
docker compose logs -f --tail=100 api worker
```

Регистрация webhook — отдельная явная команда; приложение не меняет существующие подписки само при старте. Токен MAX передаётся только в Authorization, секрет входящего webhook проверяется через `X-Max-Bot-Api-Secret`.

Ссылки вложений скачиваются только по HTTPS из `MAX_DOWNLOAD_HOSTS`, с проверкой каждого redirect и ограничением размера. Если MAX использует новый CDN, проверьте домен в реальном ответе официального API и добавьте его в настройку. Не используйте произвольные домены из текста сообщения.

## Хранение и поведение при ошибках

Для новых рабочих фотографий:

```text
MAX_PHOTOS/
  2026-10-01/
    12_мкр/
      12_мкр_УРНЫ_123.jpg
  ДАТА_НЕ_ОПРЕДЕЛЕНА/
    МР_НЕ_ОПРЕДЕЛЕН/
      МР_НЕ_ОПРЕДЕЛЕН_НЕ_ОПРЕДЕЛЕНО_124.heic
```

Новые тестовые оригиналы находятся в отдельной корневой папке `MAX_PHOTOS_TRAINING/`. Старые файлы сохраняют прежний уровень чата; начиная с 0007 отдельная задача переносит тестовые оригиналы из рабочей папки в TRAINING и обновляет ссылки. В режиме обмена по умолчанию все поступления тестовые, рабочий приём включается отдельно на странице «Обмен с АРМ».

Пробелы и недопустимые символы в компонентах пути заменяются на `_`. Уникальность имени обеспечивает ID фотографии. Неизвестная дата получает отдельную папку, а не выдуманную дату съёмки. При ручном исправлении система переносит оригинал и обновляет путь только после подтверждения Яндекс.Диска.

Полный исходный файл временно хранится в volume `photo_data` (`/data/spool`). После подтверждённой загрузки и коммита БД удаляется только локальная копия оригинала; превью остаётся в `/data/previews`. При сбое OCR/AI оригинал не теряется и не отклоняется. При сетевом сбое worker повторяет задачу, максимальная задержка — один час. Повторить раньше можно в разделе «Обработка» или карточке фотографии.

Неизвестные дата/координаты/вид работы, выход за границы и пересечения дают NEEDS_REVIEW. Исправление координат автоматически определяет микрорайон. При пересекающихся границах исправьте полигоны либо координаты: вручную выбирать микрорайон в обход географии нельзя. Все NEEDS_REVIEW считаются принятыми в ответах бота.

Несколько вложений одного MAX-сообщения обрабатываются отдельно, ответ — один. Независимые сообщения не объединяются по близости времени: это могло бы смешать разные отправки. Повтор одного webhook не создаёт новый набор.

У MAX нет документированного ключа идемпотентности для отправки ответа. Если процесс остановится сразу после успешного HTTP-ответа MAX, но до коммита `reply_sent_at`, возможен повтор **ответа бота**. Повторного файла и OCR из-за этого не будет. При ошибке сохранения одного вложения общий ответ ждёт восстановления; успешно сохранённые вложения не обрабатываются заново.

## Отчёты и проверка

- После входа открыт вчерашний день в `APP_TIMEZONE`. Очередь ручной проверки по умолчанию показывает все даты.
- По умолчанию период относится к дате фотографии; если она отсутствует, используется дата получения в часовом поясе сервиса. Можно переключить отчёт на дату получения.
- «Принято системой» = ACCEPTED + NEEDS_REVIEW; отдельный показатель показывает требующие проверки. Дубли/пересылки/отклонения учитываются отдельными записями без сохранённого оригинала.
- Список, показатели, разбивки, матрица и Excel используют одну функцию фильтрации. ID микрорайона `0` и вид работы `NONE` означают «не определён».
- Ручная проверка хранит исходный ответ AI и отдельный итог оператора. Исправление полей и задача перемещения записываются в одной транзакции. Пока worker перемещает файл, карточка показывает «Ожидает».
- В столбце «Оператор» у автоматически распределённых нейросетью фотографий показано «Нейросеть». После ручной проверки показывается имя оператора. Эта подпись используется и в Excel.
- При конфликте версий карточка возвращает 409 и предлагает обновить данные. Это защищает изменения другого оператора от перезаписи.

## Оформление панели

Нажмите на аватар или имя внизу боковой панели, чтобы открыть «Настройки». В дополнительном столбце выберите раздел: «Оформление» с иконкой палитры, «Уведомления» с колокольчиком или «Безопасность» со щитом или «Активные сеансы» с иконкой устройства. Справа отображается выбранный раздел; в «Безопасности» находится смена пароля. На узком экране столбец показывает иконки с подписями при наведении. Выбранный раздел сохраняется в адресе страницы. В разделе «Оформление» доступен переключатель тёмной темы для всей панели. Выбор сохраняется в текущем браузере и восстанавливается при следующем открытии; фотографии не меняют цвета. В светлой теме акценты зелёные, в тёмной — синие. Переключение доступно всем пользователям, включая операторов без доступа к другим разделам.

## Чаты операторов

Раздел «Чаты операторов» доступен каждому вошедшему пользователю, включая администраторов
и операторов без прав на рабочие разделы. Выберите коллегу в списке или найдите его по имени.
Личная переписка хранится в базе; читать сообщения могут только отправитель и получатель.
Администратор не получает доступ к чужим диалогам. В списке коллег отображаются их аватарки.

Новые сообщения появляются автоматически без перезагрузки. Счётчики непрочитанных показаны
в списке диалогов и боковом меню. Открытый видимый диалог отмечается прочитанным до загруженного
сообщения; отправитель видит отметку прочтения. Ранние сообщения загружаются отдельной кнопкой.
Черновики сохраняются при переключении диалогов, пока раздел открыт.

Сообщение может содержать до 4000 символов. Enter отправляет его, Shift + Enter добавляет строку.
Повторная отправка после сетевого сбоя с тем же идентификатором не создаёт дубль.
Отключённому оператору нельзя отправить новое сообщение; прежняя переписка остаётся доступной
второму участнику. Рабочие сообщения из MAX продолжают обрабатываться в разделе «Чаты MAX».

API: `GET /api/operator-chats` — список коллег и последних сообщений,
`GET /api/operator-chats/unread` — личный счётчик,
`GET /api/operator-chats/{peer_id}/messages` — история с `before_id` или `after_id` и `limit` до 100,
`POST /api/operator-chats/{peer_id}/messages` — отправка `{body, client_id}` (UUID),
`POST /api/operator-chats/{peer_id}/read` — отметка прочтения `{through_id}`.
Все запросы требуют входа, изменения также проверяют CSRF и Origin.
Миграция `0018` создаёт таблицу сообщений при штатном `docker compose up -d --build`.

## Аватарка профиля

Откройте «Настройки» → «Профиль», выберите фотографию и нажмите «Сохранить аватарку».
До сохранения доступен предпросмотр. После сохранения аватарка сразу появляется в боковой панели.
Её можно заменить или удалить; без фотографии показывается первая буква имени.
Доступно каждому вошедшему пользователю, включая операторов без прав на рабочие разделы.

Принимаются JPG, PNG, WEBP и GIF до 5 МБ и 25 мегапикселей. Сервер берёт первый кадр,
учитывает ориентацию, обрезает изображение по центру и сохраняет JPEG 256 × 256 без метаданных.
Аватарка хранится в базе аккаунта и сохраняется между входами и перезапусками контейнеров.
Замена и удаление доступны только владельцу; изменения проверяют сеанс, CSRF и Origin.
В личном профиле изображение доступно владельцу, а в чатах аватарку видят вошедшие коллеги.

`PUT /api/auth/avatar` принимает исходные байты файла, `DELETE /api/auth/avatar` удаляет аватарку.
Ответы входа, `/api/auth/me`, загрузки и удаления содержат `avatar_url` либо `null`.
`GET /api/auth/avatar/{user_id}` возвращает изображение текущего пользователя без кеширования.
Обновление устанавливается штатным `docker compose up -d --build`; контейнер `migrate`
применяет миграцию `0017`, добавляющую поле аватарки.

## Активные сеансы

В «Настройки» → «Активные сеансы» пользователь видит только собственные незавершённые входы. Текущий сеанс выделен отдельно; показаны устройство и браузер по User-Agent, известный IP-адрес, время входа и последней активности. Это сведения, сообщённые браузером и сервером, а не проверенный паспорт устройства. Точная модель компьютера и город не определяются; внешние сервисы геолокации не вызываются. IP берётся из адреса клиента ASGI с учётом настроенных доверенных прокси; произвольный заголовок X-Forwarded-For не используется. За прокси может отображаться его внутренний адрес.

Можно завершить отдельный другой сеанс или все остальные после подтверждения. Текущий вход сохраняется; на завершённых устройствах следующий запрос потребует входа заново. Кнопка «Выйти» завершает текущий вход. Управление собственными сеансами доступно и операторам без дополнительных прав; администратор также не получает доступ к чужим сеансам через этот интерфейс. Изменения записываются в журнал. Обычный срок входа остаётся `SESSION_HOURS` (по умолчанию 12 часов), истёкшие сеансы в список не входят.

API: `GET /api/auth/sessions` возвращает `items` и `session_hours`; публичный UUID `id` сеанса независим от токена входа. `DELETE /api/auth/sessions/{id}` завершает только собственный другой активный сеанс. `POST /api/auth/sessions/revoke-others` возвращает число завершённых входов в `revoked`. Изменяющие запросы требуют сеансовый cookie, CSRF-токен и допустимый Origin. Токены, их хеши и исходный User-Agent не выдаются. Последняя активность сохраняется не чаще раза в минуту после завершения запроса; вспомогательная запись не фиксирует незавершённые изменения обработчика и не восстанавливает отозванные входы.

Требуется миграция `0015` и обновление компонентов одной версией. Она сохраняет действующие входы и выдаёт им UUID. Ранее неизвестное время входа остаётся неопределённым; устройство и адрес старого входа уточняются при следующем использовании, если браузер и сервер передают эти данные.

## Уведомления о новых фотографиях

В «Настройки» → «Уведомления» можно независимо включать сообщение на экране и звуковой сигнал; по умолчанию включены оба. Выбор сохраняется отдельно для каждого пользователя в текущем браузере и синхронизируется между его вкладками. Звуковой сигнал формируется локально. Для звука браузеру требуется первое нажатие на странице; скачивание аудиофайлов и внешние сервисы не используются.

Пока панель открыта, она проверяет новые поступления раз в 10 секунд, а также при возвращении во вкладку и восстановлении сети. Справа сверху появляется уведомление с переходом к фотографии или списку. Несколько новых снимков объединяются в одно сообщение и один сигнал; вкладки одного пользователя согласуют воспроизведение звука через Web Locks и локальное хранилище (если браузер поддерживает их). Старые фотографии при открытии панели и включении уведомлений принимаются за исходное состояние и не вызывают сигнал. Исправления уже известных записей не считаются поступлением. При отключении обоих переключателей или выходе из аккаунта проверка прекращается.

Лёгкий `GET /api/photos/arrivals` возвращает только `{"photo_ids": [123, 124]}` для доступных фотографий, полученных за последние 24 часа; исходные изображения и OCR-данные не загружаются. Требуется право `photos_view`. Спам, скрытые записи, отклонённые вложения и пересланные сообщения исключены. Сравнение набора ID учитывает позднее завершение параллельной обработки запросов MAX и сохраняет исходное состояние при сбоях сети. Закрытый браузер уведомлений не получает; фоновые вкладки могут проверяться реже из-за ограничений браузера. История поступлений остаётся в разделе фотографий.

## Уведомление о новой версии

Каждая сборка панели получает собственный идентификатор и файл `/version.json`. Открытые вкладки проверяют его раз в минуту, при возвращении во вкладку и восстановлении соединения. После установки новой сборки появляется сообщение «Доступна новая версия» и кнопка «Обновить». Страница перезагружается только по кнопке; рабочие формы автоматически не сбрасываются. Ошибки сети, отсутствие или повреждение файла версии не вызывают уведомления.

Для установки обновления по-прежнему нужно обновить проект и пересобрать контейнер `web` (обычный `docker compose up -d --build` включает его). Проверка доступна после первой загрузки панели с этой функцией: ранее открытые вкладки старого приложения нужно один раз обновить вручную. Файл версии и HTML выдаются с повторной проверкой кеша, файлы сборки с хешами сохраняют длительное кеширование. В режиме разработки `npm run dev` проверка выключена.

## Права операторов

Администратор задаёт права в разделе «Операторы» → «Создать оператора» или «Изменить» → «Доступные функции». Можно выбрать функции по отдельности, применить «Обычный оператор» / «Только просмотр» или снять все галочки, оставив только личный аккаунт и смену пароля.

Право «Изменение сортировки фотографий» включается отдельно для каждого оператора. По умолчанию
оно выключено, в том числе у существующих операторов после установки обновления. Без него выбор
сортировки скрыт и всегда действует «Сначала поздние фотографии» (по дате и времени съёмки,
не получения). Правило действует также для старых ссылок, перехода к следующей фотографии,
отчётов, карты и Excel. С включённым правом доступны все четыре варианта сортировки.
Администратору они доступны всегда. Новая миграция для этого права не нужна.

Настраиваются просмотр фото, открытие оригиналов, проверка и исправление фото, доступ к спаму, скачивание Excel, удаление недоступных превью, обзор отчётов, просмотр и изменение карты, управление чатами MAX, журнал действий, очередь обработки, обмен с АРМ и обучение нейросети. Просмотр спама сам по себе не разрешает менять фотографии: для переноса в спам и возврата требуется также право на изменение фото. Повтор задачи в очереди требует права на соответствующую функцию; доступ к очереди не разрешает запускать закрытое обучение или обмен с АРМ.

Закрытые разделы и кнопки скрыты, прямые запросы API возвращают `403`. Права действуют на функции всего сервиса; разграничения по отдельным чатам и микрорайонам здесь нет. Управлять пользователями и выдавать права может только администратор. Администраторы сохраняют полный доступ независимо от галочек; защита последнего активного администратора остаётся включённой.

Миграция `0013` сохраняет прежние возможности всех существующих операторов. После изменения набора прав действующие сеансы этого оператора прекращаются, требуется новый вход. Изменение сохраняется в журнале действий. Переустановка старого кода поверх базы с ограниченными операторами недопустима: обратная миграция блокируется, чтобы не вернуть им лишние права.

API: `GET /api/meta` возвращает `permission_catalog` с кодами функций, зависимостями и исходными правами обычного оператора; `GET /api/auth/me` и административный `GET /api/users` возвращают эффективный массив `permissions`. При создании `POST /api/users` и изменении `PATCH /api/users/{id}` передаётся массив этих кодов, например `"permissions": ["photos_view"]`. Пустой массив закрывает все функции, кроме личного аккаунта. Неизвестные коды и наборы без необходимых прав на просмотр отклоняются с `422`; отсутствие поля при создании сохраняет прежние права обычного оператора, при изменении — текущие права.

## Спам при ручной проверке

Для случайного или неподходящего снимка выберите «Спам» в категории фотографии и нажмите «В спам и перейти дальше» (в очереди проверки) или «Переместить в спам». Дату, координаты и вид работы для этого заполнять не нужно.

Фото остаётся доступным в отдельном разделе «Спам», исключается из обычного списка, отчётов о работах, обычной Excel-выгрузки и будущих обучающих выборок нейросети. Оригинал переносится на Яндекс.Диске в `MAX_PHOTOS_SPAM/<training|production>/<дата>/<микрорайон>/Спам_<ID>.<расширение>` — в отдельную корневую папку рядом с `MAX_PHOTOS`. Ветка `training` содержит тестовый спам, `production` — рабочий. При недоступности Диска отметка сохраняется сразу, перенос повторяется очередью; исходный файл не удаляется. История оператора и защита от одновременного редактирования сохраняются.

Чтобы вернуть фото, откройте его в разделе «Спам», выберите обычный вид работы и сохраните. Район и статус будут рассчитаны заново, файл вернётся в обычную структуру. Если данных не хватает, фото вернётся в очередь ручной проверки. Повторная отправка того же файла в MAX не отменяет отметку спама: SHA-256 продолжает защищать от дублей.

Обновление существующей установки: `docker compose up -d --build`. Миграция `0004` добавляет признак спама и расширяет статусы без изменения существующих фотографий.

## Разработка и тесты

Python 3.12+, Node 22+, uv. Зависимости зафиксированы в `backend/uv.lock` и `frontend/package-lock.json`.

```bash
uv sync --project backend --frozen
uv run --project backend pytest backend/tests -q
uv run --project backend ruff check backend
cd frontend
npm ci
npm run build
npm test
```

Для интеграционных тестов обязательна отдельная одноразовая БД с именем, заканчивающимся на `_test`. Тесты очищают только эту явно указанную БД, применяют настоящую Alembic-миграцию и используют PostGIS.

```bash
docker run --name max-photo-test-db --platform linux/amd64 \
  -e POSTGRES_PASSWORD=test-password -e POSTGRES_DB=maxphotos_test \
  -p 127.0.0.1:55439:5432 -d postgis/postgis:16-3.5
TEST_DATABASE_URL=postgresql+psycopg://postgres:test-password@127.0.0.1:55439/maxphotos_test \
  uv run --project backend pytest backend/tests -q
```

Без `TEST_DATABASE_URL` интеграционные тесты пропускаются. Проверка реального Tesseract требует установленного бинарника; Docker-образ его содержит. HTTP-контракты MAX/Яндекс проверяются изолированно, без отправки тестовых сообщений в рабочие чаты. Для проверки реальных аккаунтов выполните сценарий в `docs/ACCEPTANCE.md`.

Локальная разработка API из `backend/`: `uv run uvicorn app.api:app --reload`; worker: `uv run python -m app.worker`; trainer: `uv run python -m app.ml`; frontend: `npm run dev --prefix frontend`. Настройте `DATABASE_URL`, `DATA_DIR` и `APP_ORIGIN=http://localhost:5173`. Vite проксирует `/api` на 8000.

## Эксплуатация

- Резервируйте PostgreSQL и volume `photo_data`, включая `/data/spool`, `/data/previews` и `/data/models`, вместе. До подтверждения Яндекс.Диска буфер может содержать единственную копию скачанного оригинала.
- Для БД: `docker compose exec -T db pg_dump -U maxphotos -Fc maxphotos > backup.dump`. Дамп и volume храните вне сервера по вашему расписанию; периодически проверяйте восстановление.
- Контролируйте место в буфере и на Яндекс.Диске, возраст ожидающих задач, раздел «Обработка», `/api/health`, логи worker и статус подписки MAX. Неполучение webhook в течение длительного времени может привести к автоматической отписке со стороны MAX.
- Масштабирование: `docker compose up -d --scale worker=2`. Задачи защищены advisory locks PostgreSQL; не используйте PgBouncer в transaction-pooling режиме для worker, которому нужны session locks.
- Контролируйте страницу «Обучение нейросети» и логи `trainer`. Сохраняемые модели/превью входят в резервную копию; удаление текущих весов или обучающих превью нарушит распознавание/дообучение. Confidence — оценка модели, не гарантированная вероятность.
- Лимит файла по умолчанию 50 MiB, изображения — 60 млн пикселей; значения меняются через `.env`. Превышение лимита отображается как ERROR и сохраняется в очереди, а не выдаётся за повреждённый файл.
- Новые версии выкатываются через `docker compose up -d --build`. Не используйте `down -v`: это удалит БД и буфер. Перед миграциями сделайте резервную копию.

Подробности: [архитектура](docs/ARCHITECTURE.md), [официальные API](docs/API_SOURCES.md), [проверка готовности](docs/ACCEPTANCE.md), [исходное ТЗ](docs/TECHNICAL_SPEC.md).

### Добавление нового чата MAX без команд на сервере

После установки обновления с миграцией `0012` откройте «Чаты MAX» → «Обнаруженные чаты». Добавьте того же бота, который подключён к сервису, в новую группу/канал, назначьте администратором и отправьте новое обычное сообщение. Список обновляется каждые 10 секунд, есть кнопка «Обновить». Он показывает точный MAX chat ID, первые 200 символов последнего сообщения и время. Нажмите «Добавить чат»: ID уже заполнен, остаётся указать название, распознавание или фиксированную маркировку и сохранить.

Обнаружение работает через действующий webhook и через тестовый polling, без переключения транспорта и повторной регистрации webhook. Оно не включает приём автоматически: до сохранения чата вложения не скачиваются, Photo/Inbox/задачи обработки не создаются. Присланные ранее фотографии нужно отправить заново после добавления. Исторические сообщения, проигнорированные до обновления, восстановить нельзя. Уже настроенные чаты, включая отключённые, повторно не предлагаются; личные диалоги и сообщения ботов не включаются в список групп. Доступ к ID и фрагментам сообщений есть только у администратора. Сохраняются только ID, короткий текст и даты, без исходного события/вложений. Повторы не создают новые строки, запоздавшее событие не заменяет более новое сообщение.

`GET /api/chats/discovered` возвращает до 100 последних ещё не настроенных чатов. MAX ID в этом методе, `/api/chats` и `/api/meta.chats` передаётся строкой, чтобы браузер сохранял все цифры 64-битного идентификатора; при сохранении принимается точная десятичная строка или целое число. Публичный контракт JSON для АРМ не меняется.

### Обмен с АРМ по кнопке

Администратору доступна страница «Обмен с АРМ»: тестовая/рабочая публикация JSON на закрытый Яндекс.Диск и переключение режима **новых** поступлений. Миграция `0006` оставляет всю прежнюю историю тестовой; старые оригиналы не перемещаются. В рабочий JSON тестовые фото не входят. Настройка нейросети и фиксированной маркировки доступна в создании и редактировании чата. Обучение модели сохраняется.

Для всех рабочих оригиналов, включая старые, структура — дата/микрорайон/файл, без папки чата. Тестовые фото имеют такую же структуру в отдельном корне TRAINING. JSON публикует отдельный контейнер `publisher`, включённый в Compose. Перед обновлением нужны резервная копия и остановка старых обработчиков. Формат, примеры, правила чтения АРМ, ограничения и порядок переключения описаны в [документации обмена](docs/exchange/README.md).

### Если оригинал удалён с Яндекс.Диска

Задача SYNC проверяет наличие и SHA256 файла, даже если путь не меняется. Если исходного файла и подтверждённого целевого оригинала нет, сервис пытается восстановить его только из сохранившейся **полной локальной копии с тем же SHA256**. Превью для восстановления не используется.

Если такой копии нет, фотография сохраняет метаданные, превью и прежний путь, а синхронизация получает ошибку `ORIGINAL_MISSING`. Задача переходит в «Приостановлено» без автоматических повторов. Повторяющиеся старые SYNC для той же фотографии объединяются при её следующей обработке; новые ручные повторы используют одну очередь. Это исправление не удаляет фотографии, разметку или оригиналы.

Чтобы восстановить синхронизацию, верните оригинал из корзины Яндекс.Диска **по прежнему пути**, затем нажмите «Проверить снова» в карточке фото или в разделе «Обработка». Если файл удалён окончательно и полной копии нет, оригинал из превью восстановить невозможно; задача может оставаться приостановленной без повторных сетевых запросов. Ошибки сети, ограничения запросов и ошибки доступа не считаются подтверждением удаления: они сохраняют автоматический повтор.

Изменение применяется после обновления API, worker и интерфейса; новая миграция БД не нужна. Старые задачи будут проверены по своему расписанию либо по кнопке «Повторить». Обновление только интерфейса не останавливает старый worker.


Миграция `0007` исправляет контракт JSON: `cohort=training`, поле `produced_at` в разделе (в индексе остаётся `published_at`). JSON хранится отдельно в `MAX_PHOTOS_ARM_EXCHANGE`, учебные оригиналы — в `MAX_PHOTOS_TRAINING`; рабочая папка `MAX_PHOTOS` не содержит эти служебные ветки. Для существующих файлов миграция ставит проверяемый перенос в очередь publisher; состояние видно на странице обмена. Старые пути фото обновляются после подтверждения переноса. Перед передачей архива заказчику дождитесь завершения этой задачи.

JSON за неизменившиеся дни и неизменившийся справочник используются повторно. Без изменений публикация создаёт только новый индекс; исправление фото создаёт файл за день первоначального поступления и индекс. Очистка сохраняет три исправные версии каждого дневного раздела и справочника, три последних индекса и 24 часа на завершение чтения вытесненных версий. Общие файлы сохраняются, пока на них ссылаются действующие индексы или подготовленные публикации. Старые JSON отправляются в корзину Диска, исходные фотографии не удаляются. Параметр окна — `EXCHANGE_READ_WINDOW_HOURS`; обновление JSON по-прежнему запускается только кнопкой. Миграция `0011` ставит проверку прежних поколений в очередь; перед обновлением нужно остановить старый publisher.


Миграция `0008` убирает ненужную прежнюю `ARM_EXCHANGE/test`, включая копию, которую предыдущая версия могла сохранить в `legacy`. Старые JSON сверяются с сохранёнными манифестами, затем служебная папка перемещается в корзину; новые копии старого обмена не создаются. При посторонних файлах очистка останавливается. Актуальные JSON остаются в отдельной папке `MAX_PHOTOS_ARM_EXCHANGE`, фотографии для заказчика — в `MAX_PHOTOS`. Выполнение требует установленного обновления и работающего publisher.

### Убрать недоступное превью

Кнопка «Убрать недоступное превью» доступна в карточке **только** при `ORIGINAL_MISSING` и ошибке синхронизации. Это не общее удаление фотографий. Перед подтверждением сервис повторно проверяет сохранённый путь оригинала, целевой путь и незавершённый перенос; при обнаружении файла на Диске или локального оригинала, конфликте версии либо недоступности Диска действие запрещено.

После подтверждения карточка исчезает из списков, спама и отчётов, её задачи SYNC останавливаются. Worker удаляет только локальные JPG-превью и временный файл превью; при сбое очистка повторяется. Оригиналы на Яндекс.Диске и файлы в локальном буфере не удаляются. В БД остаются исходный ID, хеш и история для ссылок на дубли и сверки с АРМ. Следующий JSON содержит ту же запись новой версии со статусом REJECTED, причиной `PREVIEW_REMOVED_ORIGINAL_MISSING`, `storage_status=NOT_REQUIRED` и `original_disk_path=null`. Это явное исключение записи, а не её молчаливое исчезновение из обмена.

Повторная отправка исходного файла новым сообщением MAX после очистки принимается как новая фотография. Ранее обученные веса модели очисткой превью не изменяются; скрытая запись исключена из новых обучающих выборок. Для установки требуется миграция `0009` и обновление API, worker и интерфейса. Сама миграция не удаляет существующие превью и не скрывает фотографии.


### Единая структура старого архива и отдельный спам

Миграция `0010` отменяет сохранение папки чата для старых фотографий и ставит обновление архива в очередь `publisher`. Все доступные старые оригиналы переносятся в ту же структуру, что новые:

```text
MAX_PHOTOS/<дата>/<микрорайон>/<файл>
MAX_PHOTOS_TRAINING/<дата>/<микрорайон>/<файл>
MAX_PHOTOS_SPAM/production/<дата>/<микрорайон>/Спам_<ID>.<расширение>
MAX_PHOTOS_SPAM/training/<дата>/<микрорайон>/Спам_<ID>.<расширение>
MAX_PHOTOS_ARM_EXCHANGE/…
```

Режим поступления, ID, SHA256, разметка и превью сохраняются. Путь меняется после подтверждения оригинала; перенос прерывается и возобновляется по сохранённому журналу. Недоступный оригинал получает `ORIGINAL_MISSING`, остальные фото продолжают переноситься. Пустые старые папки отправляются в корзину; папки с оставшимися файлами и корневые папки сохраняются. На время очистки сервис приостанавливает собственные переносы, чтобы они не записывали фото в проверяемые пустые папки. Во время обновления не редактируйте архив вручную на Диске.

Ошибка отдельного фото, старого обмена или переноса учебной папки больше не прерывает независимые этапы. В журнале publisher видны `archive_photo`, `archive_stage` и безопасный конкретный код ошибки. Если после перемещения старого обмена в `legacy` пути в БД не успели обновиться, контрольные суммы проверяются в обоих прежних расположениях. Манифесты БД сохраняются до завершения очистки обоих расположений. Если прежняя версия уже очистила манифест, старые JSON могут быть проверены по индексу того же экземпляра сервиса: формат, источник, поколение и SHA256 всех присутствующих файлов должны совпасть. Чужие, изменённые и не подтверждённые файлы сохраняются.

Пустые копии корневых папок вида `MAX_PHOTOS (1)` и `MAX_PHOTOS_ARM_EXCHANGE (1)` тоже отправляются в корзину. Непустые копии и действующие корни не удаляются. Перенос всей старой папки `ТЕСТОВЫЕ` откладывается, пока в ней остаются записи фото с незавершённым индивидуальным переносом.

При сообщении `no configuration file provided: not found` команда Compose запущена вне каталога проекта. Перейдите в каталог с `compose.yaml`, затем выполните `docker compose logs --tail=100 publisher`. Для этого исправления новая миграция не нужна; обновите код и контейнеры, затем повторите задачу `ARCHIVE_ORGANIZE` в разделе «Обработка» либо нажмите «Обновить структуру папок» в разделе обмена, когда задача завершена.

Для установки обновите API, worker, publisher и интерфейс, остановив старые обработчики перед миграцией. После запуска `publisher` перенос выполнится автоматически; повтор доступен кнопкой «Обновить структуру папок» на странице обмена. Рабочий сайт и реальный Диск локальными тестами не изменяются. JSON с новыми путями по-прежнему публикуется отдельно по кнопке после завершения переноса. Имя корня спама можно задать `YANDEX_SPAM_ROOT`; по умолчанию используется `<YANDEX_DISK_ROOT>_SPAM`.

### Карта фотографий

В карточке вместо полей «Адрес» и «Город» можно выбрать активный микрорайон вручную, в том числе без координат. Выбор сохраняется при синхронизации и пересчёте границ, определяет папку на Диске, отчёты и микрорайон в JSON для АРМ. Координаты не выдумываются: снимок без них остаётся в счётчике фотографий без координат и не получает точку на карте. Остальные причины проверки (например, отсутствие даты или вида работы) сохраняются. Для возврата к автоматическому определению выберите «Определять по координатам».

`PATCH /api/photos/{id}` принимает `district_id`: положительный ID задаёт ручной выбор, `null` возвращает определение по координатам, отсутствие поля сохраняет текущий режим. В карточке API поле `district_source` показывает `OPERATOR`, `COORDINATES` либо `null`. Старые поля адреса и города остаются совместимыми с API; существующие значения не удаляются. При установке применяется миграция `0016` через штатный контейнер `migrate`.

Раздел «Карта фотографий» (`/photo-map`) доступен с правом `photos_view`. По умолчанию показаны сегодняшние снимки в часовом поясе сервиса. Доступны те же фильтры, что в архиве: период, чат, микрорайон, вид работы, статус, оператор и дата снимка либо получения. При неизвестной дате снимка используется дата получения. Кнопка «На карте» в архиве переносит текущие фильтры.

Используется существующий `YANDEX_MAPS_API_KEY`. На карте вместо обычных меток показаны миниатюры фотографий. Соседние точки объединяются в группы с миниатюрой одного доступного снимка и счётчиком в углу; нажатие приближает группу, а для совпадающих координат открывает просмотр снимков. Если превью отсутствует или не загрузилось, показан значок камеры. В карточке точки — превью и ссылка на фото. Несколько фотографий с одинаковыми координатами сохраняются отдельными элементами группы. Возврат из карточки сохраняет фильтры карты. Фотографии без координат учитываются отдельным счётчиком. Скрытые превью исключены; спам доступен только при явном выборе и наличии права `spam_view`.

`GET /api/photos/map` принимает фильтры архива и возвращает компактные `items`, `summary` (всего, с координатами, без координат), `snapshot_id` и `next_after_id`. Клиент автоматически загружает порции до 1000 точек, передавая `after_id=next_after_id` и исходный `snapshot_id`, пока курсор не станет `null`. Ограничение таблицы по страницам на карту не распространяется. Верхний ID фиксирует границу новых поступлений, но не является транзакционным снимком: правки, сделанные во время загрузки, могут попасть в следующую порцию. Кнопка обновления перечитывает выборку. Оригиналы не загружаются: для видимых меток и групп запрашиваются только локальные превью, по одному на группу. Миграция БД для карты не требуется.

### Редактируемый справочник и сохранение нейросети

Раздел «Виды работ» доступен администратору: можно добавлять названия и изменять порядок/названия существующих работ. Внутренний код назначается один раз и не редактируется. Удаления работ через интерфейс нет, чтобы не потерять связи с фотографиями, правилами чатов и обучением. Переименование меняет подписи в карточках, фильтрах, отчётах и справочнике АРМ. Маркировка в имени файла на Диске остаётся прежней, поэтому переименование справочника не перемещает архив.

Миграция **0022** определяет существующую установку по наличию хотя бы одной записи в `users`, `chats`, `photos` или `model_versions`. Для неё однократно переносит все 16 прежних видов работ в `work_types`, сохраняя коды, маркировки файлов, порядок интерфейса (ГАЗОН пятый) и исходные индексы выходов модели. Фотографии, история разметки, статусы/пути моделей и файлы весов не изменяются. Чистая база нового сервера остаётся с пустым справочником и без обученной модели; создание первого администратора впоследствии не заполняет его автоматически. Один экземпляр сервиса соответствует одной компании.

Приложение не восстанавливает справочник из кода при запуске. Следующие запуски миграций выполняют только ещё не применённые версии, поэтому пользовательские названия и добавленные работы сохраняются. Новым серверам нужны отдельные пустые база и volume `photo_data`; копирование резервной копии или volume старого сервера является переносом данных, а не чистой установкой. При обновлении текущего сервера сохраняйте оба существующих volume: `postgres_data` и `photo_data` (веса и разметочные превью находятся в `/data/models` и `/data/previews`).

Для установки обновляются API, worker, trainer, publisher и интерфейс со штатным `migrate` (`alembic upgrade head`). Старые обработчики нужно остановить до миграции. Справочник встраивается в действующие фильтры, ручную проверку, фиксированные правила чатов, Excel, имена новых файлов и JSON обмена. Новые категории доступны оператору сразу; автоматическое распознавание новой категории включается только после накопления разметки и успешного обучения. Для старых моделей без `metrics.class_codes` используется замороженный порядок прежних 16 кодов; добавление/перестановка работ не расширяет и не переинтерпретирует загруженную модель. Новые версии сохраняют свой список `class_codes` в метриках, независимо от порядка интерфейса.

`GET /api/work-types` возвращает справочник; `POST /api/work-types` и `PUT /api/work-types/{id}` доступны только администратору. Изменения защищены номером версии и записываются в журнал. В обмене 1.0 код работы теперь проверяется по форме стабильного кода (до 60 символов `A–Z`, цифры и подчёркивание), а соответствие названия берётся из опубликованного `work_types`. Клиент АРМ не должен ограничивать список прежними 16 значениями; поставляемые JSON Schema обновлены.

### Общие подписи отправителей MAX

Имя отправителя хранится по ID пользователя MAX в `max_senders` и действует во всех чатах одного экземпляра сервиса, включая старые фотографии. В разделе «Чаты MAX → Участники» достаточно подписать ID один раз. Изменение подписи и «Убрать подпись везде» применяются к этому ID во всех чатах. Фотографии, их версии и исходный ID отправителя не меняются.

Миграция **0023** переносит прежние подписи из `chat_senders`. Если у одного ID разные имена, выбирается последнее изменённое (`updated_at`, затем `created_at`; при полном совпадении — меньший `chat_id`). Все исходные строки сохраняются как прежние подписи/регистрации для восстановления спорного варианта; текущая подпись берётся только из `max_senders`. При последующем явном удалении общей подписи удаляются и её ручные регистрации; сами фото сохраняются. Чистая установка получает пустой справочник отправителей. Откат с удалением общих подписей запрещён.

Списки участников и счётчики фото по-прежнему относятся только к выбранному чату. В списке показываются зарегистрированные в нём ID и отправители его доступных фото; общий справочник не раскрывает участников остальных чатов. Доступ к чатам, фотографиям и спаму проверяется как прежде. Для редактирования подписи достаточно права управления доступным чатом. Все изменения записываются в его журнал с `scope=ALL_CHATS`. Записи по разным чатам для одного ID сериализуются общей блокировкой. Для установки требуются миграция `0023`, обновлённые API и интерфейс.

### Пересылка фотографий между операторами

В карточке фотографии под кнопками сохранения доступна «Переслать фото». Выберите коллегу и при желании добавьте вопрос (например, «Какой вид работ тут выбрать?»). В личном чате появляется миниатюра со ссылкой на ту же карточку. Получатель открывает фото, затем возвращается кнопкой «К переписке» и отвечает обычным сообщением. Несохранённые поля исходной карточки при пересылке остаются на месте; сама пересылка не меняет статус, разметку, версию или файл фотографии.

Миграция **0024** добавляет `operator_messages.photo_id` и разрешает сообщение без текста только при наличии фото. Старая переписка сохраняется; ссылка на фото не создаёт копию оригинала или запись Photo. Повтор после сетевого сбоя с тем же `client_id`, получателем, текстом и `photo_id` не создаёт дубль. Использовать тот же `client_id` для другой фотографии нельзя.

Переслать фото можно только при наличии доступа к нему у обоих участников. Список получателей (`GET /api/operator-chats?photo_id=<id>`) учитывает права просмотра, доступ к исходному чату MAX, право на спам и активность аккаунта. При отправке все права проверяются снова. Доступ к редактированию для обсуждения не требуется. Если позже доступ отозван или превью скрыто, история и вопрос сохраняются, но вложение становится недоступным, без миниатюры и ссылки. Сам факт переписки не предоставляет новых прав, а содержимое сообщения остаётся доступным только его двум участникам.

`POST /api/operator-chats/{peer_id}/messages` дополнительно принимает необязательный `photo_id`; ответ и страницы переписки содержат `photo: {id, available, preview_url}` либо `null`. Из карточки, открытой по `/photos/<id>?operator_chat=<peer_id>`, возврат ведёт в `/messages?with=<peer_id>`. Для установки нужны миграция `0024`, обновлённые API и интерфейс.

### Фильтр по отправителю и компактное меню

В общей панели фильтров поле «Отправитель» выбирает фотографии конкретного пользователя MAX. Подписанные отправители отображаются с общим именем и ID; неподписанные — по ID. «Не указан» выбирает фотографии без исходного ID. Фильтр применяется к списку, очереди проверки, карте, отчётам и Excel и сохраняется при переходе к следующему фото и возврате в список. Доступны только отправители фотографий, соответствующих остальным фильтрам и разрешённым чатам. Счётчики пересчитываются по всей выборке; значения ID передаются строками без округления браузером. В API используется `sender_id`, а `GET /api/photos/filter-counts` возвращает его счётчики и `options` с доступными именами.

Кнопка рядом с надписью «Рабочее пространство» сворачивает боковую панель до значков и разворачивает обратно. Подсказки названий, непрочитанные сообщения, профиль и выход доступны в обоих режимах. Выбор сохраняется в браузере; без сохранённого выбора на узком экране используется компактный режим. На небольшом экране развёрнутое меню открывается поверх содержимого и закрывается кнопкой или нажатием вне панели. Дополнительная миграция для этих функций не требуется; обновляются API и интерфейс.

### Переход из отчёта к фотографиям

Нажатие на количество в обзоре открывает фотографии с теми же фильтрами: периодом (включая «За всё время»), отправителем, статусом и остальными выбранными условиями. «Всего в отчёте», сводки по микрорайонам, чатам, видам работ, матрица и обычный Excel исключают дубли, пересланные фотографии и спам. Дубли и пересланные остаются в своих счётчиках; нажатие открывает отдельную выборку с соответствующим статусом. Такие события не увеличивают «Не определён» и не создают пустые группы в сводках. Переходы к фотографиям отчёта получают `work_only=true`, в том числе со старых ссылок `work_only=false`. Явный статус DUPLICATE/FORWARDED по-прежнему позволяет просматривать и выгружать отдельный архив. Записи и ссылки на оригиналы сохраняются. Для установки обновляются API и интерфейс; миграция базы не требуется.

### Личный порядок бокового меню

Кнопка «Изменить порядок меню» рядом с «Рабочее пространство» включает настройку: пункты перетаскиваются мышью или перемещаются кнопками «Выше»/«Ниже» с клавиатуры и на сенсорном экране. «Сохранить» записывает порядок в аккаунт; «Отмена» возвращает сохранённый вариант. Кнопка сброса готовит стандартный порядок, который также нужно сохранить. В свёрнутой панели настройка автоматически раскрывает меню.

Порядок принадлежит пользователю и сохраняется при повторном входе, обновлении сервиса и входе с другого устройства. Недоступные по правам разделы не отображаются; их позиции сохраняются в настройке. Новые разделы, которых нет в сохранённом порядке, добавляются в конец. Домашняя страница и права доступа от перестановки не меняются.

`GET /api/auth/me` и ответ входа содержат `sidebar_order` — список путей разделов. `PUT /api/auth/sidebar-order` принимает `{"sidebar_order":["/photos","/review","/"]}` только для текущего пользователя; пустой список возвращает стандартный порядок. Действуют обычные проверки сессии, CSRF и Origin. Миграция `0027` добавляет личную настройку со стандартным пустым значением для существующих аккаунтов. Для установки обновляются API и интерфейс, миграция применяется штатным контейнером `migrate`.
