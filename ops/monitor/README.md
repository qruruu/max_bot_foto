# Локальный сборщик «Контроля сервиса»

Модуль `/ ?section=control` (без пробела) доступен только владельцу сервиса. В нём
шесть разделов: сводка, посещаемость, Метка, Сигнал, сервер и безопасность.
Операторы и администраторы организаций не получают доступ к `/api/platform/metrics`.

## Что собирается

- Посещения: собственный скрипт `/usage.js`, случайный идентификатор браузера,
  визиты после 30 минут без активности, раздел, тип устройства и источник перехода.
  В БД хранится хеш идентификатора. Полные URL, содержимое форм и география не
  собираются. Do Not Track учитывается. Владелец исключён при наличии подтверждённой
  сессии владельца на этом домене; на отдельном домене Сигнала его личность неизвестна.
- Активные аккаунты: успешный вход и последующая работа оператора/администратора
  компании или проверяющего. Учётные записи разных компаний различаются.
- Метка: фоновые снимки существующих БД компаний, рабочие и тестовые фото раздельно,
  очереди обработки/сохранения, ошибки, приостановленные задания и готовность модели.
  Период относится к дате получения фото. Текущие очереди от периода не зависят.
- Сигнал: обращения жителей без спама и внутренних обращений проверяющих,
  назначение, возраст открытых обращений, закрытия и отказы по дате решения,
  медиана времени рассмотрения, переход от открытия формы до успешной отправки.
- Сервер: CPU, iowait, load average, доступная память, подкачка, диск, сеть,
  процессы Compose, перезапуски/OOM, соединения и объём БД, резервные копии и
  результаты проверки восстановления. API-ошибки и задержки считаются отдельно
  от служебного опроса; p95 — верхняя граница интервала, не точное измерение.
- Безопасность: ошибки и успешные входы в приложение/SSH, лимиты входа, отказы
  в доступе, скачивания оригиналов и экспорты, проверки типовых служебных путей.
  Сохраняются IP и название аккаунта; пароли, токены, тела запросов/ответов,
  SQL-запросы и содержимое файлов не сохраняются.

Посещения не равны людям. Метки `from=max|telegram|vk|qr` помогают определить
источник, но посетитель может изменить их, а приложение мессенджера может не
передать referrer. Эти показатели не являются доказательством происхождения атаки.
Сбор начинается после установки обновления; прежних посещений в БД нет.

## Правила внимания

- 10 неудачных входов с одного IP за 10 минут; вход после 5 ошибок;
- срабатывание существующего ограничения попыток входа;
- вход аккаунта с IP, которого нет в его более ранней сохранённой истории;
- 100 выдач файлов, 250 МиБ либо 10 экспортов на аккаунт/IP за 10 минут;
- 20 отказов/проверок служебных ресурсов с одного IP за 10 минут;
- служебные порты БД/Redis/Docker, слушающие сетевые интерфейсы;
- изменения отслеживаемых Git-файлов и сертификаты, истекающие менее чем через 14 дней.

У тревоги есть время, источник, аккаунт и численные основания. Повторы объединяются
по правилу и источнику в пределах часа. Просмотренный сигнал сохраняется; после
нового часового окна повторное срабатывание создаёт новый сигнал. Непросмотренные
сигналы видны и вне выбранного периода. Обычные выгрузки и смена сети/VPN также
могут сработать: это основание для проверки, а не доказательство утечки.

Сборщик не заменяет IDS, аудит всех процессов, сетевой анализ или внешний монитор
доступности. Он не видит все копирования по SCP/SQL, действия вне приложения,
скомпрометированное ядро или обход журналирования. Слушающий интерфейс порт
не доказывает доступность из интернета — нужно учитывать firewall/NAT. Git-проверка
не является криптографической проверкой целостности. Авторизация и доступ к БД
не ослабляются; новых автоматических блокировок и новых внешних портов нет.

## Установка после проверки обновления

Требуются Linux, systemd, Python 3, Docker Compose, Git, journalctl, ss и openssl.
Сначала штатно обновить приложение, применить миграцию 0045 и пересобрать оба
веб-компонента: новый Nginx пишет отдельные JSON-события с фиксированной категорией
ресурса. Обычный access log сохраняется. Сборщик работает на хосте от root, читает
узкие поля состояния Docker и SSH-журнал; Docker socket внутрь приложения не монтируется.

Для проекта в `/root/max_bot_foto`:

```bash
python3 /root/max_bot_foto/ops/monitor/max_foto_monitor.py --print-only
install -m 0644 /root/max_bot_foto/ops/monitor/max-foto-monitor.service /etc/systemd/system/
install -m 0644 /root/max_bot_foto/ops/monitor/max-foto-monitor.timer /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now max-foto-monitor.timer
systemctl start max-foto-monitor.service
```

`--print-only` показывает только выбранные метрики и события безопасности: не
публиковать этот вывод, он содержит IP. Для другого расположения проекта изменить
ExecStart и передать `--project /абсолютный/путь`. Путь диска выбирается `--disk`,
конфигурация резервных копий — `--backup-config`; `--certificate /путь/fullchain.pem`
можно передать несколько раз. По умолчанию проверяются сертификаты доменов Метки
и Сигнала, настроенных в этом репозитории.

Передача — JSON через stdin локальной команды `docker compose exec -T api python
-m app.platform_monitor ingest`. Публичного endpoint для внесения метрик нет.
Работа компаний не замедляется запросами дашборда: снимки собираются фоновым
процессом, интерфейс читает сохранённые агрегаты. Зависшая/недоступная компания
получает явную отметку, а не нулевые счётчики.

Таймер запускается раз в минуту после окончания предыдущего замера. Данные старше
5 минут помечаются устаревшими. Память/диск и длительная нагрузка CPU дают
предупреждение в сводке, как и копия старше 36 часов, проверка восстановления
старше 8 дней, ошибки/блокировки задач и фото в обработке более 30 минут.

Очистку выполняет тот же сборщик: визиты и активность — 90 дней; серверные замеры,
запросы и события безопасности — 30 дней; просмотренные сигналы — 90 дней;
непросмотренные сигналы сохраняются. Для работы очистки таймер должен быть включён.
Проверять `systemctl status max-foto-monitor.timer` и журнал сервиса при отсутствии
свежих данных. Ошибки вспомогательного сбора не должны срывать вход или приём фото.
