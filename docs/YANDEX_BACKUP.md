# Фотографии с Яндекс.Диска: резервная копия и восстановление

С 29 октября 2026 года для папок сервиса настроен отдельный архив в приватном
Selectel S3 `max-foto-storage`. Он дополняет копию проекта и базы данных.

Первая копия завершилась **29 октября в 01:03 по Екатеринбургу**:
**5 580 файлов, 1,70 ГБ**, ID **`43a63d11`**. Все 5 555 оригиналов,
отмеченных в базах организаций как загруженные, сверены по SHA-256.
В 01:04 весь архив восстановлен из Selectel во временную папку: проверены
все 5 580 файлов, ошибок нет. Временная восстановленная копия удалена.

## Что происходит автоматически

- В **03:00 по Екатеринбургу** сохраняются проект, база и локальные файлы.
- В **04:00** копируются файлы из папок сервиса на Яндекс.Диске и отправляются
  в тот же зашифрованный репозиторий Selectel, отдельным комплектом.
- В **воскресенье в 06:00** архив фотографий восстанавливается во временную
  папку, а содержимое всех файлов проверяется по SHA-256.

Расписание выполняет сервер. Mac и открытый чат ему не нужны.
Для копирования Яндекс.Диска приложение не останавливается. Операции с
репозиторием используют общую блокировку с резервной копией проекта.

Список папок читается из настроек приложения при каждом запуске. Учитываются
текущие и предыдущие названия папок всех активных и приостановленных организаций:
основной фотоархив, учебные оригиналы, спам и папка обмена. Остальное содержимое
личного Яндекс.Диска не копируется. Папки, которые ещё не созданы, отмечаются
в описании комплекта. Невозможность открыть Диск завершает запуск ошибкой.

На сервере используется `rclone copy` с проверкой MD5. Это накопительная копия:
**удаление файла на Яндекс.Диске не удаляет уже сохранённый файл из архива**.
При изменении файла по тому же пути сохраняется новая версия. Restic хранит
семь последних успешных комплектов архива; неизменившиеся блоки общие.
Если старый вариант файла был перезаписан, искать его нужно в более раннем
комплекте, пока тот входит в эти семь версий. Ручные запуски тоже считаются.

Из-за сохранения удалённых файлов накопительный архив и расходы на хранение
могут расти. Новые фотографии между запусками и файлы, удалённые до первого
успешного копирования, не защищены этим архивом. Это отдельный проход по живому
Диску, а не снимок строго на одну секунду с базой данных.

Ошибка скачивания или проверки не запускает отправку нового комплекта и
очистку старых версий. Политика хранения ограничена меткой
`max-foto-yandex-complete`, поэтому не удаляет комплекты проекта с меткой
`max-foto-complete`. Удаление всего S3-репозитория по-прежнему уничтожит обе
истории: независимого второго хранилища и Object Lock здесь нет.

## Как проверить

На сервере:

```bash
max-foto-yandex-backup status
systemctl list-timers 'max-foto-yandex-backup*' --all
```

В статусе должны быть свежие даты и `"success": true` в последней попытке.
Результат последнего тестового восстановления показывается отдельно.
Общая команда `max-foto-backup status` тоже показывает состояние архива.
Уведомления о сбоях в мессенджер или почту не подключены.

Разовая копия и отдельная проверка восстановления:

```bash
systemctl start max-foto-yandex-backup.service
systemctl start max-foto-yandex-backup-verify.service
```

## Если удалена фотография

1. Посмотрите доступные комплекты фотографий:

   ```bash
   max-foto-backup restic snapshots --tag max-foto-yandex-complete
   ```

2. Выберите ID подходящей копии. Подставьте его вместо `ID_КОПИИ` и восстановите
   архив **в отдельную папку**, чтобы сначала проверить файлы:

   ```bash
   max-foto-backup restic restore ID_КОПИИ --target /srv/max-foto-yandex-recovery
   ```

3. Фотографии будут внутри:

   ```text
   /srv/max-foto-yandex-recovery/var/lib/max-foto-backup/yandex-disk/staging/files/
   ```

   Далее идут имя подключения (`default` для основного Диска либо ID другого
   подключённого аккаунта), исходная папка сервиса и её прежняя структура.
   Например: `default/MAX_PHOTOS/дата/адрес/фотография.jpg`.

4. Найдите и откройте нужный файл. В веб-интерфейсе Яндекс.Диска загрузите его
   обратно в исходную папку с прежним именем: путь хранится в базе приложения.
   Перед заменой существующего файла сохраните его отдельно. При потере самой
   базы используйте также [инструкцию восстановления проекта](BACKUP_RECOVERY.md).

Пароль шифрования и S3-ключи используются те же, что для копии проекта.
Если сервер потерян, подключите restic к сохранённому репозиторию на новой
машине и выберите комплект с меткой `max-foto-yandex-complete`. Чтобы только
скачать архив, доступ к работающему Яндекс.Диску уже не нужен.

## Где находится настройка

Программа: `/usr/local/lib/max-foto-backup/max_foto_yandex_backup.py`.
Накопительная локальная копия: `/var/lib/max-foto-backup/yandex-disk/staging`.
Результаты запусков: `/var/lib/max-foto-backup/yandex-last-*.json`.
Службы и таймеры: `/etc/systemd/system/max-foto-yandex-backup*`.

Доступ к Яндекс.Диску программа получает из контейнера API, включая подключённые
аккаунты организаций. Токены записываются во временный файл с доступом только
root и удаляются после копирования; в журнал и описание комплекта они не входят.
Уже выданный постоянный OAuth-токен не обновляется программой. После его отзыва
нужно переподключить Диск в сервисе. На новой машине для новых ежедневных копий
понадобится rclone, обе программы и службы из сохранённой конфигурации.

Справочные материалы: [rclone copy](https://rclone.org/commands/rclone_copy/),
[поддержка Яндекс.Диска и MD5](https://rclone.org/yandex/).

При первом копировании 29 октября Яндекс возвращал ошибку HTTP 500 для
18 оригиналов. Их точные байты получены из исходных сообщений MAX и сверены
по SHA-256 с метаданными Яндекс.Диска. Они включены в архив; происхождение
отмечено в `manifest.json`. Файлы на самом Яндекс.Диске при этом не заменялись.
