# Защита служебных веб-ресурсов

Оба веб-образа включают общие `frontend/nginx-security-*.conf`. Запрет выполняется
до выдачи статических файлов, SPA и передачи в API. Закрыты скрытые файлы и каталоги
(в том числе `.env`, `.git` и вложенные варианты), `/wp-admin`, `/wp-login.php`,
`/phpmyadmin`, `/vendor/phpunit`. `.well-known` оставлен для ACME и публичных метаданных;
вложенные скрытые файлы внутри него также закрыты.

Только эти служебные запросы ограничиваются по клиентскому IP отдельно в каждом
веб-контейнере: 6 в минуту, burst 5 без задержки. Разрешённые лимитом запросы получают
403 от `deny all`, превышение — 429. Обычные страницы и обычные 404 этим лимитом
не ограничиваются. Существующие лимиты входа и обращений сохраняются. Блокировок IP
на уровне firewall эта политика не создаёт.

Важен порядок фаз Nginx: `deny all` работает после `limit_req`; замена на `return 403`
обойдёт ограничитель. Общий snippet с location должен предшествовать другим regex
location. Проверка `nginx -t` сама по себе не проверяет это поведение.

В защитном location обычный access log заменяется одной записью `METKA_SECURITY_V1`:
время, IP, метод, фиксированная категория цели, HTTP-код, размер ответа, статус
ограничителя и версия правила. URL, параметры, заголовки, тело и имя запрошенного
файла в этот формат не входят. Ошибки доступа этого location не пишутся отдельно,
поскольку стандартное сообщение Nginx содержит сырой URI. Остальные журналы приложения
этой правкой не меняются.

Закрытый АРМ должен поддерживать формат V1 **до** обновления веб-контейнеров. Одна
запись не дублируется обычным access log. HTTP 200 и размер ответа не доказывают
выдачу служебного файла. Тела исторических ответов журнал не хранит.

Клиентский IP принимается только от доверенного локального reverse proxy. В production
порты контейнеров привязаны к loopback, а хостовый Nginx перезаписывает
`X-Forwarded-For` значением `$remote_addr`. До изменения цепочки прокси нужно повторить
внешний запрос с подставленным заголовком и сверить фактический адрес в журнале;
иначе ограничения могут применяться к прокси или подставленному адресу.

Проверка без production-данных: `python3 ops/test_web_security.py`. Нужен Docker.
Тест использует оба реальных конфига и временные контейнеры, проверяет запрет при
наличии тестовых секретных файлов, 403/429, отсутствие двойной/небезопасной записи,
ACME, assets, API, фотографии, экспорты, `/a/...` и обычные страницы.

Релиз требует сборки и замены только `web` и `appeals-web`: конфиги встроены в образы.
Перед обновлением сохраняются исходные конфиги и ID/теги обоих работающих образов.
Откат — восстановить эти файлы и образы и пересоздать только два веб-контейнера с
`--no-deps --no-build`. Не перезапускать БД, обработку фото или весь сервер.
