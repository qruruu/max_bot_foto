# MAX Фото → АРМ: ручная публикация JSON v1

Реализован транспортный обмен через закрытый Яндекс.Диск. АРМ читает файлы по собственной кнопке; MAX Фото публикует их по кнопке администратора «Обмен с АРМ». Новый машинный HTTP API не нужен. Договоры, дочерние работы, планы, факты и клиентские фотопакеты остаются в АРМ.

## Принятые решения владельца

- Обучение нейросети и действующий редактор геозон сохранены. Автоматическое расписание JSON не добавлено. Повторы уже запрошенной публикации выполняются автоматически после сбоя.
- Все фотографии, существовавшие до миграции `0006`, помечаются `test`. Это соответствует текущей тестовой установке. Их оригиналы, превью, разметка и пути не удаляются и не перемещаются миграцией.
- По умолчанию приём остаётся тестовым. Администратор явно переключает **будущие поступления** на `production`. Даже ещё не обработанные фотографии сохраняют режим, присвоенный при получении. Переключение обратно в тестовый режим также возможно.
- В JSON используется `cohort=training` или `production`, как в ТЗ. Внутреннее значение `test` в БД/операторской панели сохранено для совместимости и при экспорте преобразуется в `training`. Это не меняет правила обучения модели.
- Настройки классификации чата доступны при создании и редактировании. При OFF требуется один из существующих 16 кодов; OCR/GPS/SHA/хранение продолжаются. Режим, выбранный фиксированный код и версия правила записываются при поступлении и не меняют фотографии в очереди или историю.

## Файлы и идентичность

```text
disk:/<YANDEX_DISK_ROOT>/                    # Только рабочий фотоархив для заказчика
  <photo_date>/<district>/<filename>
disk:/<YANDEX_DISK_ROOT>_TRAINING/           # Тестовые и учебные оригиналы
disk:/<YANDEX_DISK_ROOT>_SPAM/               # Спам отдельно от обычных фото
  training/<photo_date>/<district>/Спам_<ID>.<ext>
  production/<photo_date>/<district>/Спам_<ID>.<ext>
disk:/<YANDEX_DISK_ROOT>_ARM_EXCHANGE/        # Служебный JSON, вне фотоархива
  training/<instance_uuid>/
    snapshots/<received_date>/<generation_id>.json
    dictionaries/<generation_id>.json
    indexes/<generation_id>.json
  production/<instance_uuid>/
    snapshots/<received_date>/<generation_id>.json
    dictionaries/<generation_id>.json
    indexes/<generation_id>.json
```

`instance_uuid` создаётся один раз миграцией и сохраняется в БД/резервной копии. `source_instance_id` равен `<instance_uuid>-test` или `<instance_uuid>-production`. Суффикс `-test` — часть уже существующего непрозрачного ID; его нельзя переименовывать в `-training`, иначе АРМ воспримет старые фото как новый источник. Значение `cohort` в JSON при этом строго `training`. Идентификатор записи АРМ — `(source_instance_id, source_photo_id)`, а не путь, хеш, название чата или время снимка. Все исходные ID передаются строками.

**Рабочий читатель АРМ должен быть настроен только на папку `<YANDEX_DISK_ROOT>_ARM_EXCHANGE/production/<instance_uuid>` и проверять `cohort=production` в индексе, каждом разделе и каждой записи.** Не обходить общую папку рекурсивно и не импортировать тестовую ветку. Таким образом старые тестовые фотографии и их будущие исправления не попадут в рабочий поток. Дубликаты определяются отдельно внутри каждого режима, поэтому рабочая повторная отправка тестового файла принимается независимо.

UUID/режим/`received_at` нельзя сбрасывать после начала обмена. Новая независимая установка получает другой UUID. При восстановлении старой резервной копии **после уже состоявшихся публикаций** остановить публикации и согласовать восстановление с АРМ: версии/поколения не должны регрессировать или повторно занять существующие пути. Обычное обновление программы не создаёт новый UUID.

## Алгоритм читателя АРМ

1. Перечислить все файлы непосредственно в `indexes/` с учётом пагинации API Диска. Имя — номер публикации из 20 цифр, например `00000000000000000042.json`. Выбрать максимальное поколение, больше последнего успешно принятого.
2. Скачать индекс авторизованным запросом, проверить `index.schema.json`, ожидаемые `source_instance_id`, `cohort`, `schema_version=1.0`. Не переходить к меньшему уже принятому поколению. При ошибке оставить прежние данные и показать состояние обмена.
3. Ссылки `file_ref` относительны корню данного контура. Запретить абсолютные пути, URL и выход через `..`. Скачать справочник и все изменившиеся разделы, сверить SHA256 **полученных байтов**, схему, идентичность источника, поколение, дату раздела и число `items`. Сумма количеств разделов должна совпасть с `index.photo_count`. Каждая запись принадлежит своему received-разделу в указанной часовой зоне. Проверить отсутствие повторяющихся source ID.
4. После проверки всего набора применить его одной транзакцией АРМ. Upsert по исходной идентичности: та же версия — пропустить, меньшая — не заменять большую, большая — обновить существующую запись. Не создавать новый объект из-за смены даты, категории, статуса или пути.
5. Запомнить принятое поколение только после успешной транзакции. Не считать отсутствие нового индекса подтверждением отсутствия новых фото в MAX: это последнее **опубликованное** состояние. Показывать `as_of` и время загрузки в АРМ.
6. Если новый индекс повреждён/не читается или не сходится хотя бы один раздел, сохранить предыдущий целый набор. На первом импорте можно проверить предыдущее поколение; оно не должно быть меньше уже принятого. Повторить чтение при следующем обновлении.

`latest.json` отсутствует намеренно: используются только неизменяемые индексы, без предположений об атомарном перезаписывании указателя Диском. Индекс загружается последним после подтверждения хешей всех файлов. Старые поколения не перезаписываются. Каждая ручная публикация формирует полный набор всех received-разделов выбранного режима, включая прошлые дни; версия каждой фотографии сохраняется, если её данные не менялись.

## Поля записи и источник

В файле раздела время формирования называется `produced_at`; в индексе время публикации — `published_at`, как в ТЗ. Формальные схемы находятся в `schemas/`. `examples/` содержит 10 **синтетических** отдельных сценариев и согласованный пример индекса/справочника. Не импортировать эти примеры как рабочие данные. Файлы сценариев независимы; `08-corrected-ordinary` — следующая версия `01-ordinary`, а не дополнительная фотография.

| JSON | Источник / правило |
|---|---|
| `source_photo_id`, `source_version` | `Photo.id` строкой, `Photo.version` целым |
| `received_at`, `updated_at` | Сохранённые поля БД с часовым поясом; received_at неизменяем |
| `photo_date`, `photo_time` | Поля Photo, `null` допустим; дата получения не подставляется |
| `max_chat_id`, `max_message_id` | Исходные MAX ID, без URL вложений, токенов или ID отправителя |
| `district_id`, `district_name` | Исходный район MAX и имя, зафиксированное при его определении/пересчёте; не территория договора |
| `district_geometry_version` | `null`: историческая версия геометрии фотографии неизвестна |
| `source_work_type_code` | Текущий `Photo.work_type`, один из существующих 16 кодов или `null` |
| `classification_mode` | Режим при получении: AI/CHAT_FIXED; для старой истории LEGACY_UNKNOWN; схема допускает REVIEW |
| `work_rule_version`, `fixed_work_type_snapshot` | Версия настройки чата и фиксированный код на момент получения; неизвестное `null` |
| `work_type_source` | Источник **текущей** маркировки AI/CHAT_FIXED/OPERATOR или `null`; ручное исправление не стирает первоначальный режим |
| `classification_confidence` | Сохранённая уверенность AI; фиксированное правило не выдумывает уверенность |
| `status`, `storage_status`, `review_reason` | Действующие значения MAX; пустой список причин передаётся как `null` |
| `duplicate_of` | ID исходной фотографии, строка или `null`; отдельного оригинала у дубля может не быть |
| `sha256` | Хеш собственного файла, либо `null` до вычисления/у дубля |
| `original_disk_path` | Закрытый сохранённый путь на Диске либо `null`; не публичная ссылка |
| `cohort` | training/production; внутренний test преобразуется в training |
| `error_code` | Сохранённый обезличенный код ошибки обработки/хранения |
| `latitude`, `longitude` | Распознанные/исправленные координаты, неизвестное `null` |

`source_work_type_code` — стабильный внутренний код, а `work_types[].name` — соответствующая короткая маркировка. Все 16 пар и действующие статусы поставляются в справочнике. Он также содержит текущий GeoJSON геозон и SHA256 сериализованной геометрии каждой зоны. Этот хеш **не выдаётся за историческую версию геометрии фотографии**. Названия районов не являются ключами и не используются для угадывания договорных ID.

Полный индекс включает все Photo выбранного режима: RECEIVED, PROCESSING, ACCEPTED, NEEDS_REVIEW, REJECTED, DUPLICATE, FORWARDED, ERROR, SPAM. Статусы хранения: PENDING, ERROR, SYNCED, NOT_REQUIRED. Неопределённое остаётся `null`. MAX не предоставляет операцию удаления Photo; записи не исчезают из публикаций из-за смены статуса, категории, спама или даты. Исправление старого фото остаётся в received-разделе первоначального поступления. PostgreSQL-триггер повышает версию при изменении любого экспортируемого состояния, включая промежуточные ошибки; очистка служебного вложения не меняет экспортируемое состояние.

Наличие пути или `SYNCED` описывает последнее подтверждённое состояние MAX, **не проверяет существование оригинала в момент чтения АРМ**. При внешнем удалении с Диска АРМ должен корректно обработать 404, не увеличивать счётчик доступных оригиналов и не уничтожать метаданные. Аналогично при PENDING/ERROR сохранённый прежний путь не доказывает готовность текущей версии. Спам, дубли, неопределённые фото не становятся принятыми договорными доказательствами автоматически.

## Надёжность и хранение

- Запрос кнопки и задача PUBLISH фиксируются одной транзакцией БД. Повторное нажатие при незавершённой публикации возвращает ту же задачу.
- Отдельный контейнер `publisher` обслуживает только PUBLISH. Основной worker продолжает фотографии/синхронизацию/ответы MAX, trainer работает как прежде. Publisher не обращается к АРМ.
- БД читается в REPEATABLE READ; полный подготовленный снимок и его пути сохраняются в `Publication.payload` перед сетевыми операциями. Повтор после перезапуска использует те же байты, а новые исправления попадают в следующую ручную публикацию.
- Загрузчик проверяет SHA256 средствами существующего адаптера Яндекс.Диска. После сбоя между разделами нет нового индекса; после сбоя сразу за загрузкой индекса уже доступен полный согласованный набор. Session advisory lock сериализует публикации, устаревшая задача не заменяет более новое завершённое поколение.
- Очередь сохраняет ошибки и повторяет попытки с существующим backoff до часа. UI показывает состояние и обезличенный код ошибки. Обновление **состояния** на странице не запускает новую выгрузку.
- Автоматическая очистка сохраняет три полностью исправных поколения каждого контура. Старое поколение можно убрать только спустя `EXCHANGE_READ_WINDOW_HOURS` (по умолчанию 24 часа) после публикации третьего более нового поколения. В течение окна поколений может быть больше трёх. Очистка запускается отдельной durable задачей EXCHANGE_GC; это не запускает новые публикации JSON по расписанию.
- Перед очисткой проверяются хеши файлов трёх сохраняемых поколений. При отсутствии/повреждении любого из них удаление не выполняется. Убираются только принадлежащие данному поколению JSON; сначала индекс, затем его разделы и справочник. Пути вне отдельной папки обмена не допускаются. Операция возобновляется после сбоя, исходные фото, Audit и обучающие материалы не удаляются.
- Старые JSON перемещаются в корзину Диска (`permanently=false`), а payload очищенного поколения удаляется из БД. Корзина очищается по правилам Яндекса; она может временно занимать место. Устаревшая выгрузка неправильного формата больше не копируется в `legacy`: после проверки по сохранённым манифестам и SHA256 служебная папка отправляется в корзину. Исходные записи Photo/Audit и фотографии сохраняются, актуальные JSON в отдельной папке обмена не затрагиваются. Если в старой папке обнаружен посторонний файл или ссылка на оригинал, очистка прекращается.
- Полный снимок собирается в памяти; для многолетнего архива нужно измерить потребление ресурсов.

## Оригиналы

Для всех рабочих фото, включая старые: `disk:/<root>/<photo_date>/<district>/<district>_<короткая маркировка>_<Photo.id>.<ext>`. Уровня чата нет. Тестовые/учебные оригиналы — в отдельной корневой папке `disk:/<root>_TRAINING/`, вне папки заказчика. Неизвестная дата и район сохраняют отдельные обозначения. Спам вынесен в `disk:/<root>_SPAM/<training|production>/<photo_date>/<district>/Спам_<Photo.id>.<ext>`. Миграция `0010` переводит старые строки на `archive_layout=district_v1` и ставит возобновляемый перенос старых оригиналов и спама в очередь publisher. Только подтверждённые пустые папки после переноса отправляются в корзину; корни и папки с файлами сохраняются. ID, режим, SHA256, разметка и превью не меняются. Старый путь может перестать работать после переноса, поэтому АРМ должен брать путь из последней версии записи. JSON с изменившимися путями публикуется по кнопке после переноса.

## Доступ и совместная приёмка

Токен MAX остаётся только в его окружении. АРМ нужен собственный OAuth-доступ с правами чтения без записи/удаления к закрытой папке обмена и нужным оригиналам. Права аккаунта/папок и OAuth scope должны проверяться совместно; нельзя считать, что приватный путь сам по себе ограничивает права токена. Яндекс документирует раздельные scopes `cloud_api:disk.read` и `cloud_api:disk.write` в [перечне сервисных прав](https://yandex.ru/dev/api360/doc/ru/ref/ServiceApplicationsService/ServiceApplicationsService_Create). Конкретную схему аккаунтов/доступа нужно подтвердить на установленном Яндекс.Диске. MAX не создаёт публичные ссылки и не передаёт свой токен в JSON.

Реальные ACL и встречный читатель АРМ этим изменением не настраивались: в локальных тестах используются подставные MAX/Диск. Перед запуском проверить отдельным читателем: чтение индекса/раздела/оригинала разрешено; запись и удаление запрещены; анонимное чтение запрещено. Получить первоначальный снимок, повторить без дублей, исправить старую запись, проверить неизвестные значения, отключить сеть, восстановить обмен, убедиться в исключении всей тестовой ветки. Неизменяемый индекс является одним из разрешённых ТЗ способов публикации; значения cohort и поле produced_at приведены к исходному контракту.

## Обновление установки и откат

1. Проверить установленный SHA и текущие миграции. Создать резервную копию БД/тома и проверить восстановление отдельно. Не применять эту миграцию к иной установке, где старая история уже рабочая: здесь **вся старая история становится тестовой** по решению владельца текущей установки.
2. На время обновления остановить приём/worker/trainer/publisher, выполнить миграции до `0008` и запустить собранные компоненты одной версии. В Docker Compose добавлен publisher; обычное обновление проекта включает его. Не запускать старую программу параллельно с новой моделью режимов.
3. Миграция `0007` повышает версии старых test-записей (публичное значение cohort теперь training), прекращает повторы уже подготовленных снимков неправильного формата и ставит задачу ARCHIVE_ORGANIZE. Publisher переносит существующие тестовые оригиналы из рабочей папки в TRAINING с проверкой SHA256 и обновлением Photo/Audit; прежнюю ТЕСТОВЫЕ переносит за пределы архива заказчика. Миграция `0008` отдельно ставит повторную организацию для установок, уже завершивших старую версию переноса: ненужная ARM_EXCHANGE удаляется в корзину как из фотоархива, так и из ранее созданной legacy/ARM_EXCHANGE. Новая копия старой выгрузки не создаётся. По манифестам публикаций и SHA256 проверяется весь состав старой папки, включая все страницы списка. При посторонних файлах, изменённом хеше или ссылке на оригинал задача останавливает очистку. Актуальный JSON остаётся на Яндекс.Диске отдельно от фото. Доступные рабочие оригиналы не перемещаются. Это описание задачи версии 0007/0008; версия 0010 обновляет также старую структуру рабочих фото, TRAINING и спама. Если исходный файл уже удалён, это фиксируется аудитом и не восстанавливается из превью.
   Перед каждым переносом цель и SHA256 фиксируются в Audit. Перенос возобновляется после сбоя, в том числе после перемещения файла до коммита Photo и последующей правки даты оператором. Его можно повторно запустить кнопкой «Убрать служебные файлы из папки заказчика»; перед передачей папки заказчику убедиться, что задача завершена. Обновить тестовую публикацию и проверить АРМ. Затем включить рабочий приём при готовности установки. Обновление уже работающей установки не переключает её обратно в test.
4. Для `0007` downgrade не понижает версии и не возвращает служебные файлы в папку заказчика. Для `0006` до публикаций/новых рабочих фото/фиксированной маркировки допускается downgrade. ## Исключение недоступного превью

Сервис позволяет убрать из панели только превью с подтверждённым отсутствием оригинала. Физическая строка Photo и ссылки duplicate_of сохраняются. После этого источник публикует прежний source_photo_id с увеличенным source_version, status=REJECTED, review_reason=["PREVIEW_REMOVED_ORIGINAL_MISSING"], storage_status=NOT_REQUIRED и original_disk_path=null. АРМ должен применить исключённое состояние к существующей записи, а не создавать новую и не считать её доступным доказательством. Отметка передаётся при следующей ручной публикации; ранее опубликованные поколения не переписываются. JSON Schema v1 не меняется: используется существующий статус и список строковых причин.


При установке `0010` остановите старые API/worker/publisher до миграции и запуска обновлённых процессов. На странице обмена показана отдельная папка спама и состояние задачи `archive-organize:v4`. Кнопка «Обновить структуру папок» повторяет эту задачу без создания параллельных дублей. Во время переноса не меняйте архив вручную на Диске. Если файл отсутствует и полной локальной копии нет, сервис сохраняет превью и историю, отмечает ORIGINAL_MISSING и продолжает обработку остальных файлов.
