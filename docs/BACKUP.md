# Резервное копирование MAX Фото на LogosIT

Подробное объяснение настройки, состава копии и действий при удалении проекта
или потере всего сервера: [BACKUP_RECOVERY.md](BACKUP_RECOVERY.md).

Этот документ описывает отдельную систему резервного копирования приложения в
приватный Selectel S3 `max-foto-storage`, регион `ru-1`. Наличие файлов в
`ops/backup` само по себе не означает, что расписание установлено: проверяйте
состояние служб на сервере.

## Состав и согласованность

Один комплект содержит:

- логическую выгрузку PostgreSQL/PostGIS в формате `pg_dump -Fc` и список ролей;
- полный Docker volume `max-photos_photo_data`, включая буфер оригиналов,
  превью, модели и остальные файлы;
- `/root/max_bot_foto`, включая `.env`, исходный код, Compose и Git;
- настройки Nginx, сертификаты Let's Encrypt и конфигурацию резервного копирования;
- описание версии приложения, образов контейнеров, числа строк в таблицах и
  контрольные суммы файлов.

Не включаются старые локальные архивы из `backups`, переустанавливаемые
зависимости `.venv`/`node_modules`, кэши и сборки интерфейса. Существующие
локальные архивы не удаляются. Данные другого Compose-проекта не копируются.
Фотографии с Яндекс.Диска сохраняются отдельным ежедневным архивом:
[состав, расписание и восстановление фотографий](YANDEX_BACKUP.md).

Основной объём файлов предварительно копируется при работающем приложении.
Затем контейнеры проекта, кроме БД, штатно останавливаются, файловая копия
обновляется и создаётся выгрузка БД. После этого ранее работавшие контейнеры
запускаются обратно и проверяется их работоспособность. Во время этого короткого
этапа интерфейс и приём данных могут быть недоступны. Выгрузка в S3 и очистка
старых версий выполняются уже после запуска приложения.

При ошибке приложение запускается обратно через `finally` и `ExecStopPost`.
Дополнительная служба при загрузке ОС восстанавливает состояние после
внезапного отключения сервера. Параллельные копии и проверки исключены блокировкой.

## Хранение и расписание

- Ежедневная копия: **03:00 Asia/Yekaterinburg** (22:00 UTC предыдущего дня).
- Хранятся **7 последних успешно завершённых копий**.
- Проверка полного чтения, файловых сумм и восстановления БД в изолированном
  временном контейнере: **воскресенье, 05:00 Asia/Yekaterinburg**.
- Отдельный архив папок сервиса на Яндекс.Диске: **ежедневно, 04:00**;
  проверка восстановления фотографий — **воскресенье, 06:00**.
- Пропущенное из-за выключения сервера расписание выполняется после запуска.
- Репозиторий: `s3:https://s3.ru-1.storage.selcloud.ru/max-foto-storage/max-foto/restic`.
- Используется restic, шифрование на сервере до отправки и повторное
  использование неизменившихся блоков между версиями. Это снижает занимаемый объём.

Очистка ограничена отдельным репозиторием, меткой `max-foto-complete` и хостом
`LogosIT`. Неуспешная отправка не запускает удаление предыдущих копий.

## Проверить состояние на сервере

```bash
systemctl list-timers 'max-foto-backup*' --all
max-foto-backup status
journalctl -u max-foto-backup.service -n 30 --no-pager
```

Разовая копия и отдельная проверка:

```bash
systemctl start max-foto-backup.service
systemctl start max-foto-backup-verify.service
```

Ошибка копирования отмечается состоянием failed в systemd и файлом
`/var/lib/max-foto-backup/last-attempt.json`, результат проверки восстановления —
файлом `last-verification.json` в той же папке. Уведомления в мессенджер или по почте
не настроены. Следите за балансом Selectel и свежестью `last-success.json`.

## Секреты и восстановление

Конфигурация находится в `/etc/max-foto-backup`, доступна только root.
`credentials.json` содержит S3-ключи, `repository-password` — отдельный пароль
шифрования restic. Пароль шифрования необходим даже при наличии S3-ключей.
Храните его копию вне сервера. Он также сохранён на Mac в игнорируемом Git файле
`.env.max-foto-backup-recovery`; значения нельзя публиковать или коммитить.

Для аварийного восстановления сначала подготовьте отдельную машину с restic,
Docker и PostgreSQL 16/PostGIS 3.5. Верните конфигурацию доступа из сохранённого
файла и менеджера паролей; не выводите значения в публичные журналы.

Просмотреть версии и восстановить файлы в отдельную папку можно установленной
обёрткой (она подставляет параметры закрытого репозитория):

```bash
max-foto-backup restic snapshots --tag max-foto-complete
max-foto-backup restic restore ID_ВЫБРАННОЙ_КОПИИ --target /srv/max-foto-recovery
```

Файлы комплекта окажутся внутри
`/srv/max-foto-recovery/var/lib/max-foto-backup/staging/`. Перед использованием
проверьте `manifest.json` и `file-checksums.json`. Верните папку `project` в
отдельный каталог развёртывания, `photo_data` — в отдельный Docker volume.
Создайте пустую PostgreSQL/PostGIS БД на основе `template0` (например,
`createdb --template=template0 maxphotos`), чтобы в ней ещё не было схем
`tiger` и `topology`. Загрузите `postgres.dump` с помощью
`pg_restore --exit-on-error --no-owner --no-privileges`. Учетные записи и пароль
БД должны соответствовать сохранённому `.env`; роли при необходимости
восстанавливаются по `postgres-roles.sql`.

Проверяйте восстановленный сервис с выключенными обработчиками MAX,
публикацией, загрузками и обучением, чтобы не обработать рабочие сообщения
повторно. Переключать рабочий домен и запускать обработчики следует только
после проверки файлов, базы, разметки и настроек. Автоматическое тестовое
восстановление поднимает только изолированную БД без сети и не запускает приложение.
