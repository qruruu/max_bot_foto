# ТЕХНИЧЕСКОЕ ЗАДАНИЕ

## 1. Название проекта

Сервис автоматического приёма, анализа, классификации и хранения фотографий, поступающих из разрешённых групповых чатов мессенджера MAX, с операторской веб-панелью, картой микрорайонов, хранением файлов на Яндекс.Диске и формированием отчётности.

---

## 2. Цель проекта

Необходимо разработать полноценный рабочий сервис, который:

1. Получает фотографии и файлы-изображения из определённых разрешённых чатов MAX.
2. Проверяет, можно ли принять фотографию.
3. Не принимает пересланные сообщения.
4. Не принимает повторные файлы-дубли.
5. Считывает непосредственно с изображения:
   - дату;
   - время;
   - координаты;
   - при наличии — адрес и город.
6. По координатам автоматически определяет микрорайон.
7. Анализирует содержимое фотографии и определяет вид выполненной работы.
8. Сохраняет фотографии на Яндекс.Диск.
9. Переименовывает фотографии по микрорайону и виду работы.
10. Хранит полную информацию о фотографиях в PostgreSQL.
11. Отвечает в MAX, принята фотография или не принята.
12. Если вид работы автоматически определить невозможно или на фотографии обнаружено несколько возможных видов работ — сохраняет фотографию, но помещает её в очередь на ручную проверку оператором.
13. Если дата или координаты не распознаны — фотография тоже сохраняется и отправляется на ручную проверку.
14. Предоставляет веб-панель для операторов.
15. Предоставляет карту, где администратор может рисовать границы микрорайонов.
16. Предоставляет ежедневные отчёты и экспорт в Excel.
17. Поддерживает роли ADMIN_OPERATOR и OPERATOR.

Необходимо реализовать не демонстрационный прототип, а рабочий сервис, подготовленный к развёртыванию на сервере.

---

## 3. Общая архитектура

Предпочтительная архитектура:

- Backend: Python + FastAPI.
- База данных: PostgreSQL.
- Геоданные: PostGIS.
- ORM: SQLAlchemy.
- Миграции: Alembic.
- Frontend: React / Next.js либо другой современный frontend-фреймворк.
- Фоновая обработка: worker-задачи.
- При необходимости Redis + Celery/RQ/аналог.
- Хранение фотографий: Яндекс.Диск.
- Карта: OpenStreetMap + Leaflet либо аналог.
- Интеграция с MAX: официальный MAX Bot API.
- OCR: отдельный сервис.
- Анализ вида работ: Vision/Multimodal AI.
- Docker.
- Docker Compose.
- `.env` для всех секретов.

Архитектура должна позволять менять OCR и AI-модель без переписывания основной бизнес-логики.

## 4. Интеграция с MAX

Создать бота MAX.

Использовать актуальную на момент разработки официальную документацию MAX Bot API.

Перед реализацией интеграции проверить актуальные методы API.

Бот должен работать только в заранее разрешённых чатах.

## 5. Разрешённые чаты

В базе данных должен существовать справочник разрешённых чатов MAX.

Для каждого чата хранить минимум:

- внутренний ID;
- MAX chat ID;
- название чата;
- признак активности;
- дата добавления;
- дата последнего изменения.

Пример:

| ID | MAX chat_id | Название | Активен |
|---|---|---|---|
| 1 | 123456 | Чат 1 | Да |
| 2 | 123457 | Чат 2 | Да |

Если сообщение поступило из чата, которого нет в справочнике разрешённых чатов, оно не должно обрабатываться.

ADMIN_OPERATOR должен иметь возможность:

- добавить чат;
- изменить название;
- включить;
- отключить;
- удалить или деактивировать.

Изменение списка чатов не должно требовать изменения исходного кода.

---

## 6. Какие сообщения должен обрабатывать бот

Бот должен обрабатывать изображения:

1. Отправленные как фотография.
2. Отправленные как файл с расширением изображения.

Допустимые расширения:

```python
IMAGE_EXTENSIONS = {
    ".jpg",
    ".jpeg",
    ".png",
    ".gif",
    ".tif",
    ".tiff",
    ".bmp",
    ".heic",
    ".webp",
}
```

Для анимированного GIF допускается использование первого кадра для анализа.

Все остальные типы файлов системой не принимаются.

---

## 7. Проверка пересланных сообщений

Пересланные фотографии и файлы не должны приниматься системой.

Если MAX API показывает, что сообщение является пересланным:

- файл не сохранять;
- OCR не запускать;
- AI не запускать;
- на Яндекс.Диск не загружать;
- отправить ответ:

```text
❌ Не принято: пересланные фотографии не принимаются.
```

---

## 8. Проверка дублей

Дубликаты определяются по SHA-256 исходного файла.

После скачивания изображения необходимо вычислять SHA-256.

В базе должен быть уникальный индекс или эквивалентная защита.

Если SHA-256 уже есть в базе:

- повторно файл не сохранять;
- OCR не запускать;
- классификацию не выполнять;
- сообщить:

```text
❌ Не принято: фотография уже была отправлена.
```

Дубликатом считать идентичный файл независимо от:

- чата;
- отправителя;
- даты;
- времени.

Perceptual hash в первой версии не требуется.

---

## 9. Обработка альбома / нескольких фотографий

Если одним сообщением или альбомом отправлено несколько изображений, каждое изображение обрабатывается отдельно.

После обработки всего набора отправляется одно итоговое сообщение.

Пример:

```text
✅ Обработано фотографий: 10
Принято: 8
Не принято: 2
```

Фотографии со статусом NEEDS_REVIEW входят в число «Принято».

---

## 10. Что считать принятой фотографией

Фотография считается принятой системой, если:

- сообщение не переслано;
- формат допустимый;
- файл не является дублем;
- файл удалось скачать и открыть.

Если дату, координаты или вид работы автоматически определить невозможно, фотографию не отклонять.

Она должна быть сохранена и направлена оператору.

---

## 11. Статусы фотографии

Использовать статусы:

- `RECEIVED`
- `PROCESSING`
- `ACCEPTED`
- `NEEDS_REVIEW`
- `REJECTED`
- `DUPLICATE`
- `FORWARDED`
- `ERROR`

---

## 12. Ответы бота в MAX

### Успешно распознано всё

```text
✅ Принято
Микрорайон: 12 мкр
Вид работы: Очистка урн от мусора
```

### Вид работы не распознан

```text
✅ Принято
Микрорайон: 12 мкр
```

Не писать, что фото отправлено оператору.

Не указывать вид работы.

### Микрорайон не определён

```text
✅ Принято
```

### Дубль

```text
❌ Не принято: фотография уже была отправлена.
```

### Пересланное сообщение

```text
❌ Не принято: пересланные фотографии не принимаются.
```

### Неподдерживаемый формат

```text
❌ Не принято: неподдерживаемый формат файла.
```

### Повреждённый файл

```text
❌ Не принято: файл изображения повреждён или не читается.
```

## 13. OCR изображения

На фотографии непосредственно присутствуют:

- дата;
- время;
- координаты;
- иногда адрес;
- иногда город.

Вид работы текстом на фотографии не написан.

Для OCR предусмотреть отдельный модуль:

```text
OCRService
```

Основной backend не должен зависеть от конкретного OCR-движка.

Сохранять полный распознанный OCR-текст.

---

## 14. Распознавание даты

Из изображения необходимо определить дату.

Поддержать минимум:

- `01.10.2026`
- `01-10-2026`
- `01/10/2026`
- `01.10.26`
- `2026-10-01`

После OCR дату валидировать.

Внутренний формат:

```text
YYYY-MM-DD
```

Например:

```text
2026-10-01
```

---

## 15. Распознавание времени

Если на фотографии есть время, его необходимо извлекать.

Поддержать минимум:

- `11:43`
- `11:43:25`

Хранить отдельно:

```text
photo_time
```

Например:

```text
11:43:00
```

---

## 16. DateTimeParser

Создать отдельный модуль:

```text
DateTimeParser
```

Он должен принимать OCR-текст и возвращать:

- дату;
- время;
- confidence, если возможно;
- исходную строку.

Пример входа:

```text
30.09.2026 11:43
```

Результат:

```text
photo_date = 2026-09-30
photo_time = 11:43:00
```

---

## 17. Если дата не распознана

Фотографию всё равно принять.

Статус:

```text
NEEDS_REVIEW
```

В панели оператора должна быть возможность вручную указать дату.

После изменения даты необходимо:

- обновить запись в базе;
- переместить фотографию в правильную папку Яндекс.Диска.

---

## 18. Координаты могут быть в разных форматах

Система не должна рассчитывать только на один формат записи координат.

Координаты могут быть написаны, например:

```text
61,1060N 72,5780E
```

или:

```text
61.1060N 72.5780E
```

или:

```text
N61,1060 E72,5780
```

или:

```text
N 61.1060 E 72.5780
```

или:

```text
61,1060 N 72,5780 E
```

или:

```text
61.1060 72.5780
```

или:

```text
61°06'21.6"N 72°34'40.8"E
```

или:

```text
61°06.360'N 72°34.680'E
```

---

## 19. CoordinateParser

Создать отдельный модуль:

```text
CoordinateParser
```

Он не должен зависеть от OCR-движка.

Pipeline:

```text
изображение
↓
OCR
↓
полный текст
↓
CoordinateParser
↓
определение формата
↓
нормализация
↓
latitude / longitude
↓
валидация
↓
определение микрорайона
```

---

## 20. Поддерживаемые форматы координат

Поддержать минимум:

1. Decimal Degrees.
2. Decimal Degrees с N/S/E/W.
3. N/S/E/W до числа.
4. N/S/E/W после числа.
5. Градусы + десятичные минуты.
6. Градусы + минуты + секунды.
7. Точку как десятичный разделитель.
8. Запятую как десятичный разделитель.
9. Дополнительные пробелы.
10. Разные варианты расположения символов.

---

## 21. Правила N/S/E/W

Учитывать:

- `N` — положительная широта.
- `S` — отрицательная широта.
- `E` — положительная долгота.
- `W` — отрицательная долгота.

Пример:

```text
61.1060N = +61.1060
61.1060S = -61.1060

72.5780E = +72.5780
72.5780W = -72.5780
```

---

## 22. Нормализация координат

Все распознанные координаты приводить к единому формату:

```text
latitude: float
longitude: float
```

Пример:

```text
61,1060N 72,5780E
```

преобразовать в:

```text
latitude = 61.1060
longitude = 72.5780
```

---

## 23. Валидация координат

Обязательно проверять:

```text
-90 <= latitude <= 90
-180 <= longitude <= 180
```

Невалидные координаты не использовать.

---

## 24. Проверка координат относительно обслуживаемой территории

Если координаты формально валидные, но находятся далеко от всех нарисованных микрорайонов, фотография должна попадать в:

```text
NEEDS_REVIEW
```

Это необходимо для защиты от OCR-ошибок.

В БД хранить:

- `ocr_coordinates_raw`
- `coordinate_format`
- `coordinate_parse_confidence`
- `latitude`
- `longitude`
- полный `ocr_raw_text`

## 26. Если координаты не распознаны

Фотографию не отклонять.

Статус:

```text
NEEDS_REVIEW
```

В панели оператора предоставить поля:

- широта;
- долгота.

После ручного ввода координат система должна автоматически определить микрорайон.

---

## 27. Распознавание адреса и города

Если OCR видит:

```text
26 Парковая улица
Нефтеюганск
```

это тоже желательно сохранить.

Поля:

- `ocr_address_raw`
- `detected_address`
- `detected_city`

---

## 28. Адрес не используется для определения микрорайона

Это принципиальное правило.

Микрорайон определяется только по координатам.

Не использовать для определения микрорайона:

- адрес;
- название города;
- название чата;
- имя файла;
- текст сообщения.

---

## 29. Микрорайоны

Микрорайон определяется исключительно по координатам фотографии.

Для этого использовать географические полигоны микрорайонов.

Предпочтительно PostGIS.

---

## 30. Страница карты микрорайонов

В административной части должна быть отдельная страница:

```text
Микрорайоны / Карта
```

На ней отображается интерактивная карта.

---

## 31. Что может делать администратор на карте

ADMIN_OPERATOR должен иметь возможность:

- создать новый микрорайон;
- указать название;
- нарисовать polygon;
- нарисовать multipolygon;
- редактировать границы;
- удалить или деактивировать микрорайон;
- изменить название;
- видеть все микрорайоны одновременно.

## 32. Пример микрорайона

Название:

```text
12 мкр
```

или:

```text
Микрорайон 12
```

## 33. Point-in-polygon

После получения координат выполнить географическую проверку.

Пример:

```text
POINT -> POLYGON
```

Если точка попадает в полигон:

```text
district_id = соответствующий микрорайон
```

---

## 34. Координаты вне всех микрорайонов

Если координата не попала ни в один микрорайон:

```text
district_id = NULL
status = NEEDS_REVIEW
```

---

## 35. Координата попала сразу в несколько микрорайонов

Если полигоны пересекаются и точка попадает сразу в несколько:

```text
status = NEEDS_REVIEW
```

## 36. Пересечения полигонов

При создании или редактировании микрорайонов система должна предупреждать о пересечении полигонов.

Желательно запрещать сохранение пересекающихся полигонов без явного подтверждения администратора.

9. Содержание детских, спортивных, тренажерных площадок

11. Подметание территории
12. Промывка урн с дезинфицирующими средствами
13. Уборка зеленых зон и газонов под грабли

16. Мойка брусчатки

18. Уборка снега на площадках после снегопада

## 38. Внутренние коды видов работ

Не использовать только русские строки.

Использовать стабильные внутренние идентификаторы.

Например:

```python
WORK_TYPES = {
    "DEICING_MANUAL": "Распределение противогололедных материалов вручную",
    "SNOW_MANUAL": "Уборка снега вручную",
}
```

Реализовать такие коды для всех видов работ.

Для этого использовать Vision/Multimodal AI.

WorkTypeClassifier

AI получает:

## 42. Формат ответа AI

Пример успешного ответа:

```json
{
  "result": "SINGLE",
  "work_type": "Очистка урн от мусора",
  "confidence": 0.93,
  "alternatives": []
}
```

Если определить нельзя:

```json
{
  "result": "UNKNOWN",
  "work_type": null,
  "confidence": 0.28,
  "alternatives": []
}
```

Если определено несколько:

```json
{
  "result": "MULTIPLE",
  "work_type": null,
  "confidence": 0.55,
  "alternatives": [
    "Уборка газонов от мусора",
    "Уборка зеленых зон и газонов"
  ]
}
```

## 43. Confidence threshold

Порог автоматического принятия должен быть настройкой.

Например:

```text
WORK_TYPE_CONFIDENCE_THRESHOLD=0.80
```

Если:

- результат SINGLE;
- категория входит в список;
- confidence >= threshold;

тогда работу можно принять автоматически.

---

## 44. Что считать непринятым по виду работ

В разделе ручной проверки должны отображаться фотографии, где:

1. вид работы вообще не распознан;
2. AI увидел несколько видов работ.

Такие фотографии бот всё равно считает принятыми.

---

## 45. Только один итоговый вид работы

На одну фотографию назначается только один итоговый вид работы.

Если AI увидел несколько видов:

- автоматически ничего не назначать;
- оператор выбирает один основной вид.

```text

```

---

## 48. Причины попадания в ручную проверку

Фотография попадает туда, если:

- вид работы не распознан;
- несколько видов работ;
- дата не распознана;
- координаты не распознаны;
- координаты вне всех микрорайонов;
- координаты попали в пересекающиеся полигоны;
- иная исправимая ошибка распознавания.

---

## 49. Интерфейс ручной проверки

Слева:

- большая фотография.

Справа:

- дата;
- время;
- координаты;
- адрес;
- город;
- микрорайон;
- чат;
- AI результат;
- confidence;
- alternatives;
- причина проверки.

---

## 50. Выбор вида работы оператором

На экране должны быть доступны все 22 вида работ.

Оператор выбирает один.

После выбора:

- сохранить значение;
- записать audit log;
- переименовать файл;
- изменить статус на ACCEPTED, если других проблем нет;
- автоматически открыть следующую фотографию.

---

## 51. Ручное исправление даты

Оператор может вручную изменить дату.

После изменения:

- обновить БД;
- перенести файл в правильную папку Яндекс.Диска.

---

## 52. Ручное исправление координат

Оператор может изменить:

- latitude;
- longitude.

После сохранения координат система автоматически пересчитывает микрорайон.

---

## 53. Яндекс.Диск

Все изображения хранить на Яндекс.Диске.

Корневая папка:

```text
MAX_PHOTOS
```

---

## 54. Структура хранения

Использовать:

```text
MAX_PHOTOS/
    YYYY-MM-DD/
        Название чата/
            файлы
```

Пример:

```text
MAX_PHOTOS/
└── 2026-10-01/
    ├── Чат 1/
    │   ├── 12мкр_урны_839201.jpg
    │   ├── 12мкр_подметание_839202.jpg
    │   └── 7мкр_НЕ_ОПРЕДЕЛЕНО_839203.jpg
    └── Чат 2/
        └── 12мкр_механизированная_уборка_839210.jpg
```

---

## 55. Имена файлов

Имя файла должно содержать:

- микрорайон;
- сокращённое название вида работ;
- уникальный идентификатор.

Например:

```text
12мкр_урны_839201.jpg
```

Не использовать только:

```text
12мкр_урны.jpg
```

---

## 56. Если вид работы не определён

Имя:

```text
12мкр_НЕ_ОПРЕДЕЛЕНО_839203.jpg
```

Если микрорайон тоже не определён:

```text
МР_НЕ_ОПРЕДЕЛЕН_НЕ_ОПРЕДЕЛЕНО_839203.jpg
```

---

## 57. Переименование после ручной проверки

Если оператор выбрал вид работы:

Было:

```text
12мкр_НЕ_ОПРЕДЕЛЕНО_839203.jpg
```

Стало:

```text
12мкр_уборка_газонов_839203.jpg
```

## 58. Хранение оригинала

На Яндекс.Диск загружать оригинальный файл без ухудшения качества.

Для OCR и AI допускается временная конвертация HEIC/TIFF/BMP в JPEG/PNG.

Оригинал не менять.

- иметь Excel;
