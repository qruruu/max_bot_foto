# API приложений: фотографии, геозоны и изменения

API v1 предназначен для серверных приложений и внешних отчётов. Он не изменяет
фото, справочники, права пользователей или содержимое Диска. Требуется включённый
режим организаций (`ORGANIZATIONS_ENABLED=true`). Общий префикс:
`https://<домен-Метки>/api/integration/v1`. Префикс `/org/...` для этого API не используется.

## Выдача ключа

Администратор открывает организацию → **API-ключи** → задаёт название приложения,
срок (1–365 дней, по умолчанию 90) и права:

| Право | Разрешает |
| --- | --- |
| `photos:read` | Метаданные фото, включая спам, дубли, пересланные и их статусы |
| `geozones:read` | Справочник микрорайонов (ID, название, активность) |
| `work_types:read` | Полный справочник видов работ (системный код, название, активность) |
| `changes:read` | Журнал изменений только сущностей, на чтение которых есть права |
| `originals:read` | Получение оригиналов по ID |

Ключ закрепляется за одной организацией и **текущим режимом фотографий** (учебным
`test` или рабочим `production`). Смена режима в панели не расширяет выданный доступ.
Скрытые после очистки превью фото исключены; скрытие создаёт запись удаления для API.
Другие организации и другой режим недоступны, даже если их ID известны. Все поля
`id` имеют смысл внутри организации; храните привязку данных к организации и режиму.
Геозоны здесь — существующий справочник `districts` («Микрорайоны»), не планы
маршрутов и не контуры домов. Геометрию этот контракт не выдаёт.

Полное значение ключа показывается один раз. Сервер хранит только SHA-256 случайного
секрета с 384 битами энтропии. Ключ нельзя восстановить из списка. Сохраните его в
защищённых настройках серверного приложения. Не размещайте его в JavaScript браузера,
URL, Git, чатах и журналах. В production и создание ключей, и API требуют HTTPS.
При ротации старый ключ немедленно отзывается, новый получает те же права и режим,
срок 90 дней. После ротации требуется новая начальная выгрузка: курсоры связаны с ключом.
Не более 20 одновременно действующих ключей на организацию. В списке видны название,
права, срок, отзыв и время последнего разрешённого обращения.

Каждый запрос содержит заголовок:

```http
Authorization: Bearer <ключ-из-защищённых-настроек>
```

Cookie, пароль оператора и заголовки выбора организации не заменяют ключ.
В примерах ниже `BASE` — HTTPS-адрес с префиксом `/api/integration/v1`, `API_KEY`
получен приложением из защищённого хранилища. Не включайте трассировку HTTP и печать
заголовков в рабочей среде. Значения примеров и фотографии вымышленные.

## Начальная выгрузка

1. Создайте снимок: `POST /snapshots` с JSON `{}` для всех дат либо
   `{"photo_date":"2026-11-05"}` для одной даты. Это временная копия результатов
   чтения; рабочие фотографии не изменяются.
2. Сохраните `id` снимка и начальный `cursor`. **Не заменяйте** локальные рабочие
   данные, пока весь снимок не загружен. Создавайте отдельный временный набор.
3. Прочитайте `GET /snapshots/{id}/photos?limit=100` и, при наличии права,
   `GET /snapshots/{id}/geozones?limit=100`. Когда `next_after_id` не `null`,
   передайте его следующим запросом как `after_id`. Каждая сущность идёт по ID
   по возрастанию. Параметр `limit` — 1–100, `after_id` — целое ≥ 0.
4. После получения всех страниц атомарно замените локальный набор и сохраните
   начальный курсор. С этого курсора читайте изменения. События во время выгрузки
   уже находятся в журнале, даже если фото было удалено между страницами.
5. Освободите снимок через `DELETE /snapshots/{id}` (ответ 204). Его курсор продолжает
   работать. Снимок живёт 24 часа, на ключ допускаются два неистёкших снимка.

```bash
curl --fail-with-body "$BASE/snapshots" \
  -H "Authorization: Bearer $API_KEY" -H 'Content-Type: application/json' \
  -d '{"photo_date":"2026-11-05"}'
```

Пример ответа 201 (реальный курсор — непрозрачная подписанная строка):

```json
{
  "id": "44444444-4444-4444-8444-444444444444",
  "expires_at": "2026-11-06T07:00:00Z",
  "cursor": "<сохранить-без-изменений>",
  "photo_date": "2026-11-05",
  "timezone": "Asia/Yekaterinburg",
  "cohort": "production"
}
```

Пример страницы фотографий:

```json
{
  "items": [{
    "id": 123,
    "photo_date": "2026-11-05",
    "photo_time": "09:25:00",
    "captured_at": "2026-11-05T09:25:00+05:00",
    "received_at": "2026-11-05T09:26:12+05:00",
    "district_id": 7,
    "work_type": "BIN_EMPTYING",
    "status": "ACCEPTED",
    "is_spam": false,
    "is_forwarded": false,
    "duplicate_of": null,
    "is_defect": false,
    "original_available": true,
    "original_url": "/api/integration/v1/photos/123/original"
  }],
  "next_after_id": null,
  "cursor": "<тот-же-начальный-курсор>",
  "timezone": "Asia/Yekaterinburg"
}
```

`photo_date` — **дата работы/съёмки**, распознанная или исправленная оператором,
в часовом поясе сервиса (сейчас Екатеринбург). Отбор использует именно её: выбранный
локальный календарный день от 00:00 включительно до 00:00 следующего дня исключительно.
Это календарное поле, а не преобразованный момент загрузки. Если дата неизвестна,
она равна `null`, фото попадает в снимок всех дат, но не в дневной снимок.
`photo_time` — локальное время съёмки или `null`; `captured_at` содержит UTC-смещение
только когда известны оба поля. `received_at` — отдельный достоверный момент приёма
с UTC-смещением; он никогда не подменяет время съёмки. Момент в точности 00:00
относится к новому дню, а 23:59:59 — к текущему.

Неопределённые микрорайон и вид работы — `district_id: null` и `work_type: null`.
`work_type` — стабильный код вида работы. Название микрорайона берётся из геозон:
`{"items":[{"id":7,"name":"7 мкр","active":true}],"next_after_id":null,...}`.
Неактивные микрорайоны сохраняются в справочнике, чтобы старые отчёты могли показывать
названия. Для обычного отчёта применяйте нужные правила статусов и флагов явно:
API отдаёт разрешённые записи, включая спам и дубли, без неявного исключения из отчёта.

## Справочник видов работ

`GET /work-types` с правом `work_types:read` возвращает все настроенные виды работ
организации в порядке её справочника, включая сезонные работы и работы без фотографий.
Результат не зависит от выбранной даты, снимка или режима фотографий. В пустом
справочнике `items` — пустой массив.

```bash
curl --fail-with-body "$BASE/work-types" -H "Authorization: Bearer $API_KEY"
```

```json
{
  "items": [
    {"code":"BIN_EMPTYING","name":"Очистка урн","active":true}
  ]
}
```

`code` соответствует полю `work_type` в фотографиях и сохраняется при переименовании.
В текущей модели все настроенные виды работ активны, поэтому `active` всегда `true`.
Справочник обновляется повторным GET. Журнал `/changes` его не включает.
Для доступа выпустите ключ с отмеченным правом «Справочник видов работ».
Ранее выданные ключи сохраняют свои права и получат 403 на этом маршруте.

## Изменения и удаления

```bash
curl --fail-with-body --get "$BASE/changes" \
  -H "Authorization: Bearer $API_KEY" \
  --data-urlencode "cursor=$CURSOR" --data-urlencode 'limit=100'
```

```json
{
  "items": [
    {"sequence":104,"at":"2026-11-05T07:01:00+00:00","entity":"photo","id":123,"operation":"upsert","data":{"id":123,"photo_date":"2026-11-06","photo_time":null,"captured_at":null,"received_at":"2026-11-05T09:26:12+05:00","district_id":7,"work_type":null,"status":"NEEDS_REVIEW","is_spam":false,"is_forwarded":false,"duplicate_of":null,"is_defect":false,"original_available":false,"original_url":null}},
    {"sequence":105,"at":"2026-11-05T07:02:00+00:00","entity":"photo","id":124,"operation":"delete","data":null}
  ],
  "has_more":false,
  "cursor":"<следующий-курсор>"
}
```

Порядок `sequence` общий для фото и геозон внутри базы организации. Пропуски нормальны:
в них могут быть события другого режима или сущностей без выданного права. События
фиксируются триггерами PostgreSQL в той же транзакции, что изменение данных. Общая
строка счётчика сериализует записи до commit, поэтому поздно завершившаяся транзакция
не теряется за уже выданным курсором. Копирование снимка и его исходный курсор защищены
тем же замком; снимок не меняется при перелистывании. Создание снимка ограничено
30 секундами SQL и ожиданием блокировки 10 секунд; на большой базе выбирайте дату.
Копии снимков занимают дополнительное место в базе; освобождайте их после загрузки.

Применяйте `upsert` заменой записи по `(entity,id)`, `delete` — удалением по тому же
ключу. Изменения содержат полное состояние разрешённых полей на момент события.
Геозоны также дают `upsert` при переименовании и `delete` при удалении. Смена режима
фото или скрытие после очистки создаёт `delete` в прежней области доступа.

Изменения **не ограничены датой начального снимка**: приложение с дневным отчётом
должно удалять из локальной выборки фото, чья новая `photo_date` уже не равна дате
отчёта; добавлять подходящие вновь; применять каждую запись удаления. Иначе перенос
на другую дату оставит устаревшее фото. Идентификатор старой геозоны в удалении
не требуется — связь уже хранится в локальной записи фото.

Сохраняйте результаты страницы и новый курсор одной локальной транзакцией. При
сбое повторяйте запрос со **старым** курсором. Повторные события применяются
идемпотентно; одинаковые `sequence` не означают новую фотографию. При `has_more:true`
читайте следующую страницу сразу; при `false` сохраните курсор и повторяйте опрос
с разумным интервалом, например 30–60 секунд. Не вычисляйте курсор самостоятельно.

Журнал сохраняет события минимум 30 дней. Просроченные префиксы очищаются при
создании следующего снимка, поэтому фактическое хранение может быть дольше. Курсор
действует 30 дней после выдачи/успешного чтения. Если он старше оставшегося журнала,
подписан для другой истории либо снимок истёк, сервер возвращает 410: загрузите
новый полный снимок, **замените**, а не дополните прежний локальный набор и начните
опрос с нового курсора. Неверная подпись/чужой ключ возвращают 400.

После восстановления базы из резервной копии перед открытием API необходимо
сменить `integration_clock.epoch` на новый UUID в восстановленной базе и удалить
`integration_snapshots` (строки снимков удаляются каскадно). Это делает старые курсоры
недействительными даже если номера событий после восстановления уже успели
повториться. Сама процедура резервного копирования этим API не меняется.

Точечное чтение актуального состояния: `GET /photos/{id}`, `GET /geozones/{id}`.
Невидимые и чужие ID возвращают одинаковый 404. При остановке/удалении организации
любой дальнейший запрос ключа отклоняется; приложение должно прекратить опрос и
обработать доступность своего локального набора согласно договорённости с владельцем.
Удаление организации не даёт ключу доступ к архиву другой компании или её удалениям.

## Оригиналы

`original_url` — относительный авторизованный маршрут этой же «Метки». Передавайте
тот же Bearer-ключ при каждом GET. Он выдаёт файл с `Content-Disposition: attachment`;
API не перенаправляет на Яндекс.Диск, не выдаёт его токен, путь или постоянную публичную
ссылку. Эта ссылка не требует обновления по таймеру: проверка ключа происходит при
каждом скачивании. Если путь на Диске меняется, ID-маршрут остаётся тем же.
При отсутствии `originals:read` поле ссылки равно `null`. Оригинал может ещё загружаться
(409), исчезнуть вместе с фото (404) или быть временно недоступным (502).
Размер файла ограничен 50 МиБ и существующим лимитом загрузчика сервиса.

Для соблюдения лимита файл сначала ограниченно скачивается во временный каталог,
после чего проверяется ключ ещё раз и резервируется фактический размер выдачи.
Лимит относится к передаче клиенту; скачивание из хранилища само по себе не считается
выдачей пользователю. Разрешённая передача, начатая до отзыва ключа, может завершиться.

## Лимиты, ошибки и мониторинг

На ключ: 60 запросов/минуту и 256 МиБ/минуту; на организацию в сумме по всем ключам:
180 запросов и 512 МиБ/минуту. Смена IP не сбрасывает лимиты: счётчики и блокировки
находятся в общей БД. Окна календарные, по 60 секунд UTC. Для метаданных резервируется
верхняя граница 2 МиБ на запрос (и столько же — максимальный размер JSON-страницы),
для оригинала — фактический размер перед началом выдачи. Ошибки/прерванные передачи
могут использовать уже зарезервированный бюджет. На входе Nginx дополнительно
ограничивает попытки по IP: 10/с, burst 60. Штатные разрешённые выгрузки не приводят
к автоматической блокировке DLP. На 429 учитывайте `Retry-After` (60 секунд из API)
и повторяйте с паузой, не создавайте новый ключ для обхода ограничения.

| Код | Действие приложения |
| --- | --- |
| 400 | Исправить запрос/курсор; проверить HTTPS |
| 401 | Остановить опрос, получить действующий ключ у администратора |
| 403 | Запросить нужное право у администратора |
| 404 | Удалить недоступную ссылку/проверить ID; не перебирать чужие ID |
| 409 | Оригинал ещё не готов либо лимит активных снимков |
| 410 | Полная пересинхронизация новым снимком |
| 413 | Уменьшить страницу; для файла проверить ограничение размера |
| 422 | Исправить дату, UUID или диапазон параметров |
| 429 | Подождать и повторить без изменения курсора |
| 502/503/504 | Повторить с задержкой, сохранив прежний курсор |

Закрытый мониторинг получает отдельную подтверждённую `application_id` (публичный
ID ключа), организацию, категорию операции, результат и измеренный объём отправленных
ASGI-буферов. Пользовательские `actor_id` и `role` для приложения остаются пустыми.
Тела, файлы, ключи, заголовки, полные URL и подписанные ссылки в эти записи не попадают.
Учёт сетевого ответа означает передачу буферов сервером, не подтверждение прочтения
клиентом. Выдача внешней ссылки в старых маршрутах по-прежнему отличается от скачивания.
Группировка приложений в DLP выполняется по ID ключа и организации, независимо от IP.
Существующая политика предупреждений/критичных событий и исключение превью/публичных
изображений из счётчика файлов сохранены.

## Установка и проверка

Нужна миграция **0050** общей базы **и всех баз организаций** через штатную команду
`python -m app.cli migrate`, затем обновлённые API и web. На время миграции остановите
обработчики штатным порядком, принятом для обновления сервиса. Настройка внешнего
HTTPS-прокси должна перезаписывать `X-Forwarded-Proto` реальной схемой; web доступен
только через доверенный локальный прокси. Uvicorn не должен быть открыт наружу.

В проекте `metka-monitor` вместе с API обновлены `application_audit.py` и `data_rules.py`:
их необходимо установить на мониторинг одновременно, чтобы он принимал записи
схемы 2. VPN, SSH, резервное копирование и защитные пороги не меняются.
Для маршрута `/work-types` нужна версия `application_audit.py`, которая принимает
операцию `work_types`. Сам маршрут использует существующий справочник без миграции.

Автотесты: `backend/tests/test_integration_api.py`,
`backend/tests/test_security_telemetry.py`, `metka-monitor/tests/test_ids_dlp.py`.
Тесты баз данных запускать только с отдельной `TEST_DATABASE_URL`, имя базы должно
заканчиваться `_test`: тестовая фикстура очищает её схему.
